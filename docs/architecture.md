## 设置文件

设置窗口里的每一项都存在 `%APPDATA%\WinShun\WinShun.ini`，直接改这个文件也会立即生效：

```ini
[Launcher]
DoubleCtrl=true          ; 双击 Ctrl 呼出
DoubleCtrlPauseInGames=true       ; 前台程序独占全屏、或藏起并锁住鼠标（转视角）时不响应双击 Ctrl
DoubleCtrlPauseInFullScreen=false ; 任何程序铺满显示器时都不响应（视频、幻灯片、F11 网页）
DoubleCtrlExcludedApps=  ; 不响应双击 Ctrl 的程序，如 TheFinals.exe，逗号分隔
Hotkey=                  ; 额外的全局快捷键，例如 Alt+Space、Ctrl+Shift+F
DialogJump=true          ; “打开”“另存为”对话框里按 Ctrl+G，转到文件管理器（资源管理器、Total Commander、Directory Opus）正在显示的文件夹
DialogBar=true           ; “打开”“另存为”对话框下方的搜索框
DialogAutoJump=false     ; 对话框出现时（以及从文件管理器换了文件夹再切回来时）自动转到文件管理器的文件夹
DialogBarExcludedApps=   ; 不显示搜索框的程序，如 notepad.exe，逗号分隔；搜索框“更多”菜单里加，设置里删
FileManager=explorer     ; explorer | totalcmd | dopus：打开文件夹、打开所在位置用哪个；没装或没启动起来就用资源管理器
Renderer=d3d11           ; d3d11（文字清晰）| software（省内存，文字偏模糊）；没写或旧版的 auto：装机内存 ≥ 8 GB 用 d3d11，否则 software

[Appearance]
Theme=system             ; system（跟随 Windows 的浅色 / 深色）| light | dark
Language=system          ; system（Windows 显示语言是中文就用中文，否则英文）| zh | en

[Update]
Automatic=true           ; 启动时和之后每 12 小时到 GitHub 检查新版本

[Index]
ExcludedPaths=...        ; 不建索引的文件夹，支持 %WINDIR% 这类环境变量，逗号分隔
ExcludedNames=...        ; 任意位置的同名文件夹，也可写尾部路径，如 .svn/pristine
IncludeRemovableDrives=false
RescanOnStartup=true     ; 启动 15 秒后在后台核对一次磁盘，补上程序未运行期间的变化

[Content]
Enabled=true             ; 文件内容搜索的总开关。关掉：搜索框里没有“内容”、“全部”只按名字找、不读文件内容，内容索引清空不建（AI 的 search_content 也报已关闭）
Documents=true           ; 也搜 Word、Excel、PowerPoint、PDF 和 WPS 文件（由 WinShunExtract.exe 读）
Extensions=txt, md, ...  ; 内容搜索的纯文本扩展名，逗号分隔
MaxFileSizeMB=64         ; 文本和日志（以及下面几类以外的扩展名）超过此大小不搜内容
MaxCodeFileSizeMB=8      ; 源代码（.c .cpp .py .js …）的上限：更大的多是打包压缩后的脚本
MaxDataFileSizeMB=16     ; 数据和网页（.json .xml .svg .html .sql …）的上限：更大的多是导出的数据
MaxDocumentFileSizeMB=512 ; 文档（Word、Excel、PowerPoint、PDF、WPS）的上限：大多是图片；每个最多读出 16 MB 文字
IncludeSystemFolders=false ; “内容”范围也搜系统、程序目录和 node_modules 等（文件多，会慢不少）
Index=true               ; 建立内容索引（中日韩文字，和三个字符一段的英文、数字、空格和标点；NTFS 磁盘，后台建立，几十万个文件约占一百 MB 磁盘）

[Clipboard]
Enabled=true             ; 记录剪贴板历史；第一次运行时和 Windows 自带的剪贴板历史开关一致
WinV=false               ; 用 Win+V 打开，代替 Windows 自带的剪贴板（资源管理器重启或下次登录后生效）
Hotkey=                  ; 另一个打开剪贴板的组合键，例如 Win+Alt+V
MaxItems=200             ; 分组以外最多保留几条（10–300）；默认内存超过 16 GB 200 条，否则 100 条
MaxDays=30               ; 多少天没再复制或粘贴过就删除；0 = 一直保留（分组里的都一直保留）
Images=true              ; 也记录图片
ExcludedApps=KeePass.exe, KeePassXC.exe, 1Password.exe, Bitwarden.exe ; 不记录这些程序复制的内容

[Taskbar]
WinS=false               ; Win+S 在任务栏上方打开 Win顺，代替 Windows 搜索（资源管理器重启或下次登录后生效）；Win+Shift+S 截图由 Win顺 代为打开
StartMenuTyping=false    ; 在开始菜单里打字也用 Win顺 搜索（开始菜单开着时按一下左 Alt，这一次仍用 Windows 搜索）
SearchBox=false          ; Win顺 自己的搜索框放在任务栏的图标旁边（Windows 11；放不下时不显示）

[WebSearch]              ; 网页搜索：“全部”里输入关键词打开网页，带 %s 的网址还能搜（gh WinShun）；设置里增删改、导入导出；Icon= 是用户自选图标的文件名
size=11                  ; 几个；第一次运行时写入 10 个常用网站（baidu biying bilibili zhihu weibo douyin xhs taobao jingdong fanyi）和 winshun
1\Keyword=baidu          ; 关键词：一个词，不分大小写
1\Name=百度              ; 空 = 用关键词
1\Url="https://www.baidu.com/s?wd=%s" ; %s 是要搜的文字（UTF-8 百分号编码）
1\Home=https://www.baidu.com/ ; 只输入关键词时打开的网址；空 = 搜索网址所在网站的首页
...
11\Keyword=winshun
11\Name=WinShun
11\Url=https://github.com/LingCore/WinShun ; 没有 %s：只能打开，关键词后面再跟文字就是普通搜索
11\Home=
Defaults=2               ; 写入过第几版自带网站；旧设置升到新版时只补上新加的（关键词或网站已有的不补，删掉的不再补）

[Shares]                 ; 也搜索的网络共享（设置 → 搜索范围 → 网络共享；只收录名字，不读内容）
size=1
1\Path=\\192.168.1.10\资料 ; \\服务器\共享，或其中一个文件夹；写映射的盘符（Z:\…）会换成它映射的共享
1\Name=                  ; 显示的名字；空 = 用路径

[Network]                ; 网络共享怎么读
VerifyHours=1            ; 服务器会通知变化时，每隔几小时再整个核对一遍（Samba 不通知 NAS 本机写的）；0 = 只在启动时
VerifyHoursUnwatched=1   ; 服务器不通知变化时（有的 NAS）
Threads=16               ; 一台服务器同时读几个文件夹（核对时减半）：慢的是网络往返，不是服务器
ExcludedNames=#recycle, @eaDir, ... ; NAS 和 Mac 自己的文件夹（回收站、缩略图、快照、Spotlight），只对共享生效，和 [Index] 的叠加
ExcludedFiles=._*, .DS_Store ; Mac 写到共享上的附带文件；只支持开头的 *

[Mcp]                    ; AI 助手：Claude、Cursor、VS Code 等通过 MCP 连接 Win顺（见下文“AI 助手”）
Enabled=false            ; 开着时 Win顺 在命名管道上提供 MCP 服务，AI 客户端启动 WinShunMcp.exe 就能连上；在设置里给某个客户端点“连接”会自动打开；只读的工具只看这一项
AllowOpen=false          ; 允许 AI 打开文件和文件夹（open_item、show_in_folder；以普通权限打开）
Plugins=false            ; AI 可以使用插件：manifest 写了 ai.expose 的插件，每个命令成为工具 plugin_<id>_<command>（只是查询）
PluginActions=false      ; 允许 AI 执行插件动作：再多一个 plugin_<id>_<command>_run
Clipboard=false          ; 允许 AI 读剪贴板历史（clipboard_history、clipboard_get）
ExcludedPaths=           ; 不让 AI 看到的文件夹，逗号分隔（在“不建索引的文件夹”之外再排除）

[Plugins]                ; 插件系统自己的（设置 → 插件 → 高级）
DeveloperMode=false      ; 开发者模式：记下每条发给插件 / 插件回的消息（设置页的消息记录），脚本改了就重启常驻插件

[Plugin.winshun.kill]    ; 每个用户动过的插件一节，节名是插件 id（见下文“插件系统”）；设置 → 插件 页改，手改也行
Enabled=true             ; 插件装上默认关着
Confirmed=processes, clipboard:read ; 打开开关时用户确认过的权限（没要权限的写 none）；新版本要得更多时再问一次
Keyword.kill=jc          ; 用户给某个命令改的关键字（Keyword.<命令 id>）；空 = 这个命令没有关键字
Ai=false                 ; 卡片上的“给 AI 用”关着（只在关着时写；manifest 没有 ai.expose 的插件没有这个开关）
Setting.showSystem=true  ; manifest 里声明的设置项的值（Setting.<key>），按声明的类型解释（bool / number / 文字）；password 型不在这里：存 Windows 凭据管理器 WinShun/plugin/<id>/<key>
```

修改“不搜索的文件夹”后不需要重建索引：新排除的文件夹直接从索引里去掉，取消排除的文件夹单独补读一遍。只有取消排除“文件夹名称”（它可能出现在任何位置）时才会重新读取所有磁盘。

索引、最近使用记录、收藏夹（`favorites.json`）和日志（`WinShun.log`，只记警告和错误）保存在 `%LOCALAPPDATA%\WinShun`；剪贴板历史在其中的 `clipboard\`（`clipboard.db` 和存图片的 `images\`）。

索引文件（快照 `index.bin`、内容索引的 `content\*.grams` 和文档文字 `content\*.texts`；作者电脑上 323 万项、33.7 万个文件共约 112 MB）可以在设置 → 高级 → 索引位置换到别的文件夹（`[Index] Folder`）：

- 选的是空文件夹（或里面本来就是索引）就直接用；否则在里面建一个 `WinShun` 文件夹，索引文件从不和别的文件混放，那个文件夹也不会出现在搜索结果里。先查剩余空间。
- 只接受电脑内置的硬盘（`indexfolder::onExternalDisk`）。外接盘不行：索引文件一直开着（内容索引是内存映射），盘弹不出来；不弹出直接拔掉，内容搜索读映射文件会出错，Win顺 可能崩。“外接”看 Windows 怎么认这块盘，不看插头：`GetDriveType` 是可移动磁盘（U 盘、SD 卡），或总线类型（`IOCTL_STORAGE_QUERY_PROPERTY` 的 `BusType`）是 USB、SD、MMC、1394（USB-A、Type-C、扩展坞上的移动硬盘都是 USB），或磁盘的控制器及以上的设备节点能热拔（`CM_DEVCAP_REMOVABLE`：雷电、USB4 硬盘盒，总线类型只说 NVMe）。磁盘自己能热拔不算：主板开了 SATA 热插拔时，内置硬盘也出现在“安全删除硬件”里；eSATA 和它分不出来，按内置算。
- 移动在后台进行（`IndexService::moveTo`），期间照常搜索，内容索引暂停写入：先把文件复制过去并刷到磁盘，再在新位置写一份当前的快照，然后内容索引改用新位置的段文件，最后删掉旧文件。切换之前旧文件一直在用，所以出错或中途退出都不会丢索引；失败时设置退回原处，原因显示在设置里（窗口没开时用通知）。
- 直接改 INI 也一样会移动；程序没运行时改的，启动后再搬。启动时那块盘不在（还没解锁的 BitLocker 盘也算），这次先用默认位置并提示，设置保留，下次启动再试；用回自定义位置时，默认位置里的旧索引会删掉。INI 里写的位置根本不能用（外接盘、网络位置、里面有别的文件），设置直接改回默认并提示。
- 卸载时如果选择删除数据，自定义位置里的索引文件也一起删（只删 `index.bin` 和 `content\`，文件夹空了才删）。
- 机械硬盘可以用，设置里只用灰字说明一句。判断看卷下每块物理盘的寻道开销（`StorageDeviceSeekPenaltyProperty`，查不到时 NVMe 算固态），任何一块有寻道开销就算机械硬盘；对卷句柄直接查，跨盘卷会失败。文件名搜索全在内存里，不受影响；受影响的是内容搜索在段文件里的零散读取，每次寻道约 10 ms，硬盘休眠时要等几秒转起来。所以：
  - 内容索引在机械硬盘上（或判断不出来）时，`IndexService::prewarmSoon` 把段文件预读进系统文件缓存：启动 90 秒后、搬完索引后、从睡眠/休眠恢复 30 秒后（`RegisterSuspendResumeNotification`），以及某次查询超过 50 ms（说明页已被挤出缓存）时。用 `ReadFile` 读，读进的页和映射视图共用；句柄设 `IoPriorityHintLow`，每读 1 MB 歇同样长的时间。不用后台模式（`THREAD_MODE_BACKGROUND_BEGIN`），它会连内存优先级一起降低，这些页会最先被系统回收。
  - 内容查询不在文件索引的读锁里做（先 `pinIds` 保证编号不变）：读盘慢的那几秒，索引更新和文件名搜索都不用等。

本程序原名“快搜”（QuickFind）。第一次以 Win顺 启动时，会先让还在运行的快搜退出，再把 `%APPDATA%\QuickFind`、`%LOCALAPPDATA%\QuickFind` 搬到新位置，开机自启（计划任务“QuickFind”）也换成“WinShun”，设置、索引和最近使用记录都保留。

## 性能（实测）

测试机：i9-14900HX，4 块本地磁盘，共 **316 万**个文件和文件夹。

| 项目 | 结果 |
|---|---|
| 首次建立索引（读 MFT，C 盘的 MFT 有 4.4 GB） | 约 2.6 秒（4 个盘同时读，不含保存） |
| 之后启动时加载索引 | 约 0.15 秒（329 万项），随后补读变更日志（通常几十毫秒），不再全盘重扫 |
| 保存索引 | 323 万项存成 27 MB（以前的格式 92 MB），约 0.26 秒；有改动时 30 分钟存一次 |
| 同样 316 万项改用遍历目录 | 约 7 秒（文件系统缓存已热时；冷启动要慢得多） |
| 文件名搜索 | 一般 2–3 毫秒（329 万项；单字母约 11 毫秒，几个词约 4–7 毫秒） |
| 内容搜索（查内容索引） | 33 万个候选文件：查索引 1–10 毫秒，筛出可能含有的文件约 2 毫秒（323 万项分块并行地看一遍），再只打开这些文件取行号。例如 `季度报告` 剩 25 个，一行代码 `const auto lock = index->readLock();` 剩 13 个（片段只记单词内部时是 1392 个、共 1 GB，没被 Defender 扫过时 2.7 秒才出第一条），`for (int i = 0; i < n; ++i)` 剩 148 个（以前 15.5 万个、13.9 GB）。第一批结果凑够一屏（8 行）或满 50 毫秒就显示，之后每 100 毫秒补一次 |
| 内容搜索（索引用不上：一两个英文字母，或还没收录的文件） | 开着 Windows Defender 时每个文件第一次打开约 7–10 毫秒（它要扫描），16 个文件同时读，每秒约 800 个；结果边找边显示 |
| 内容索引 | 33.7 万个文件（含约 5800 个 Word / Excel / PowerPoint / PDF）占 75 MB 磁盘（其中不同的内容 15.2 万份；“片段-文件”对每对约 0.18 字节），文档读出的文字另存 17 MB（5717 份文字里只有 2970 份不同）；文档表约 6 MB 内存，索引文件按需映射，不占私有内存。整体合并约 1.5 秒（16 个线程，含递归图二分，期间多占约 50 MB；单线程约 6 秒）。第一次建立（或升级后重建）在文件索引建好后马上开始（第一次不等登录后的半分钟），开着 Defender 时：没人用电脑约 3 分钟（实测 163–186 秒），有人在用约 5.6 分钟（`wsbench --service --content`；这两个数是下面“建内容索引时不让线程互相等”和“文档的副本只读一次”之前量的）；关掉 Defender 实时保护时 21 秒（最早 75–94 秒，后来 27 秒）；期间搜索读过的文件直接收进来 |
| 读文档 | 本机 5815 个 Word / Excel / PowerPoint / PDF / WPS 文件（10.6 GB），4 个读取进程同时读约 28 秒，8 个约 21 秒（建索引时 CPU 核数的 1/4、2–8 个，有人用电脑且文本文件没读完时只用一半；CPU 最低优先级，磁盘和内存不降）；其中 2628 个和别的文档逐字节相同（微信里的“(1)”、备份文件夹），不再读，直接用原件的结果，8 个进程读完从 19 秒降到 12 秒。读出 112 MB 文字，压缩后约 34 MB，相同的文字只存一份，存进内容索引旁的 `.texts` 文件约 17 MB。PDF 平均约 50 毫秒，最慢的（一份 53 MB 的手册）约 5 秒；Office 文件几毫秒 |
| 打开窗口 | 约 35 毫秒；第一次也只要约 60 毫秒（启动时已预先画好一次，否则第一次要 200 多毫秒） |
| 内存 | 文件名索引：329 万项约 110 MB（约 34 字节/项，其中修改时间 13 MB）。整个程序在任务管理器里约 120 MB（刚启动），打开过窗口、内容索引建好后约 140 MB；另占显存约 10–25 MB |

一般电脑有 50 万到 100 万个文件，文件名索引大约占 15–30 MB。可用 `wsbench` 在自己的机器上测（见下文）。

## 界面语言

界面文字的源文是中文（QML 的 `qsTr()`、C++ 的 `tr()`），英文翻译在 `src/app/i18n/winshun_en.ts`，编译成 `winshun_en.qm` 嵌进程序资源。切换语言时装上或卸下这个翻译器，再调 `QQmlEngine::retranslate()`，C++ 里拼出来的文字（状态栏、托盘提示等）由各自的 `retranslate()` 重算，不用重启。

改了界面文字以后：

```powershell
cmake --build --preset release --target update_translations   # lupdate：把新字符串收进 .ts
```

然后在 `.ts` 里补上英文（Qt Linguist 或直接编辑），未翻译的条目会显示中文原文。数量相关的句子用 `%n` / `%Ln` 写，英文按单复数给两种形式。英文通常比中文长，搜索框、状态栏这些一行放不下就会被截断，翻译时要短。

## 检查更新和发布

没有自己的服务器：新版本就是 GitHub 上的 Release。`Updater` 用 WinHTTP（走系统代理设置，不用给 Qt Network 带 TLS 插件）请求 `api.github.com/repos/LingCore/WinShun/releases/latest`，比较 `tag_name` 和当前版本；有新版本时在托盘提示（设置窗口开着时直接弹对话框），“去下载”用浏览器打开那个 Release 的页面。上次检查的时间、跳过的版本、上次提醒的时间存在 `%LOCALAPPDATA%\WinShun\update.ini`；同一个版本自动提醒最多三天一次，跳过的版本只在手动检查时显示。测试时可以用环境变量 `WINSHUN_UPDATE_FEED` 指向一个假的接口地址。

不做自动下载和替换：没有代码签名的程序在后台下载 exe、再改写自己的文件，正是杀毒软件启发式检测盯的行为，何况 Win顺 以管理员身份运行。FlClash 也是只提示、打开浏览器下载。

发布新版本：

1. 改 `CMakeLists.txt` 里 `project(... VERSION x.y.z)`。
2. 写 `docs/release-notes/vx.y.z.md`。更新对话框只显示其中两部分：开头一段话（中文在前、英文在后，中间以中文句号分开），以及 `## 新功能 · What's new` 下的列表（每条是 `- 图标 中文`，下一行缩进写英文）。格式见 `src/core/Release.cpp` 和单元测试。
3. 退出正在运行的 Win顺，运行 `./scripts/release.ps1 -Publish`：编译、部署，打包安装程序 `WinShun-x.y.z-x64-setup.exe` 和 `SHA256SUMS.txt`，再用 `gh` 建 `vx.y.z` 的 Release。只发安装程序，不提供免安装的压缩包（0.2.0 及更早的版本是压缩包）。

安装程序用 Inno Setup 6.5 或更新版本编译（`installer/WinShun.iss`；6.5 起才有 Windows 11 风格和深色模式的向导），脚本会先找 `%LOCALAPPDATA%\Programs\Inno Setup*` 下的，也可以用 `-Iscc` 指定。

- 装到 `Program Files\WinShun`（Win顺 本来就要管理员权限），开始菜单一个快捷方式，“设置 → 应用”里可以卸载。`AppId` 永远不要改：新版靠它找到旧版、原地覆盖。
- 安装和卸载前先让正在运行的 Win顺 退出：装过的用 `WinShun.exe --quit`，别处的旧版免安装副本给它的消息窗口发 `WM_CLOSE`（0.2.1 起会照 `--quit` 退出、先保存索引），过 15 秒还在就强制结束。
- 文件一装好就在托盘里启动（`--background`），趁最后一页还开着把第一次启动做完：新文件第一次启动时杀毒软件要逐个读一遍，慢的时候要几十秒，等点了“完成”再启动，这段时间屏幕上什么都没有，用户不知道它启动了没有。“完成”时勾着“运行 Win顺”，再启动一次就只是让已经在运行的那份打开搜索框（第二个实例把 `show` 交给它，马上就出来）；没勾，就让它退出（`CurStepChanged` 的 `ssDone`）。静默安装不显示，也不退出，和升级前一样在托盘里。第二个实例找不到正在启动的那份的消息窗口时，最多等 30 秒，再把命令发过去，只发一次（`MessageWindow::sendToRunningInstance`）。实测（2026-10-09，真的安装程序覆盖安装）：最后一页一出来就点“完成”，那份还没启动完，0.55 秒后搜索框出现在前台；不勾“运行”，0.4 秒内退出。
- 装好后，已有的开机自启任务（旧版免安装副本设的）改成启动安装的这份（安装程序运行 `WinShun.exe --take-autostart`）；卸载时只删除指向本安装目录的任务，并问是否删除 `%APPDATA%\WinShun`、`%LOCALAPPDATA%\WinShun`。
- 向导图片由 `tools/make_installer_images.py` 生成（浅色、深色两套），中文界面文字是 Inno Setup 仓库里的非官方翻译 `installer/ChineseSimplified.isl`。

## 设计取舍

- **网络共享是索引里的一种根，每个共享一条线程。** 用户在设置里加的 `\\192.168.1.10\资料` 是 `FileIndex` 里名字就叫这个的根（`walkPath` 对 `\\` 开头的路径按最长的根名前缀找），条目带 `EntryFlag::Remote`（进快照，子项继承），和本机文件一起搜、一起存进快照，重启后马上可搜。`ShareIndexer`（`IndexService` 拥有，不进它的 `Pass`：插个 U 盘、改一项设置都不打断一次几分钟的收录）给每个共享一条线程：先探测（`share::probe`：连 445 端口，像 Windows 一样发 SMB1 格式、同时提供 SMB 2 的 NEGOTIATE，对方用 SMB 2 回答才算能用，用 SMB 1 回答是只会 SMB1 的老设备；1.5 秒封顶，答案留 30 秒 / 10 秒），连得上就第一次全读（`Crawler::sync` 配 `share::Lister`：`FileFullDirectoryInfo`、64 KB 缓冲，16 个文件夹同时在路上——局域网上每次列目录要几毫秒，靠并发而不是大缓冲），之后用第二个 `ChangeWatcher` 实时跟踪（服务器支持变更通知时；本机的监听溢出、卡住都和它无关），每 1 小时再核对一遍（一轮要读很久的共享按耗时的 60 倍放宽）。实时跟踪只是加速：Samba（大多数 NAS）只通知经网络做的修改，NAS 自己的同步、下载套件直接写盘的不通知（只有共享根目录那一层例外）；`change notify = no` 的则什么都不通知，监听却照样建得起来，看不出来。离线的共享条目还在，结果调暗、标“离线”；网络变化（`NetworkNotifier`：网卡、地址、连通性）、睡眠恢复后安静 5 秒重试，否则按 1 到 10 分钟退避。
- **网络共享的一轮核对整轮成功才删除。** `Crawler::sync` 的延后删除模式：增、改照常，“磁盘上没有了”的只记下来；服务器中途掉线、或某个共享级的错误（`share::classify`），这一轮一项不删。还要防“列目录成功、却是空的”：NAS 重启后磁盘晚几十秒才挂上，那时共享真是空的。所以少的超过 max(1000, 一半) 时不删，状态记“可疑”，半小时后再读一遍结论相同（差不到一成）才删，或者用户点“按现在的内容更新”。一轮期间 `pinIds()` 挡住压缩，id 不会变；不用 `m_journaling`，快照照常保存。
- **网络 I/O 直接在提权进程里做，登录用 Windows 的凭据管理器。** 提权的 Win顺 和普通权限的资源管理器是两个登录会话，各有各的 SMB 连接；在资源管理器里输过密码、没勾“记住”的，Win顺 用不上。凭据管理器按用户、两边共用：卡片上的“登录…”弹 Windows 自己的凭据框（`CredUIPromptForWindowsCredentials`），`WNetAddConnection2` 连上（同一台服务器已经用别的账户连着时先断开），勾了“记住”就 `CredWrite` 一条以服务器为名的 Windows 凭据，资源管理器以后也不用再输。Win顺 自己不存密码。后台的核对从不弹框，只把卡片标成“需要登录”。
- **网络共享上的东西不在搜索线程和界面线程上等服务器。** 内容索引和内容搜索都跳过 `Remote` 的文件；结果里共享上的文件只用类型图标（`SHGetFileInfo` 带 `SHGFI_USEFILEATTRIBUTES`，不碰文件）；输入的 UNC 路径先探测再现场列目录（不通就只用索引里的）；回车打开、显示位置之前也先探测，连不上就在底栏说一句，不让资源管理器卡半分钟。

- **磁盘可以随时插拔。** 每个已索引的磁盘都登记了设备通知：要弹出或锁定（格式化、chkdsk）时，Win顺先关掉在这个磁盘上的所有句柄再答应；其他磁盘照常跟踪。快照按磁盘保存，磁盘增减时只读新增的那个。
- **始终以管理员身份运行，NTFS 磁盘直接读 MFT 和 USN 变更日志。** 建索引时一次顺序读完主文件表，不用逐个文件夹遍历；文件的每个硬链接都按各自的路径收录（`FSCTL_ENUM_USN_DATA` 只给一个名字，System32 里很多文件会因此丢失，所以没用它）。快照里记着每个盘的日志读到了哪里，启动时只补读这之后的记录，不再全盘重扫；运行中跟踪日志，没有 ReadDirectoryChangesW 缓冲区溢出的问题。日志被覆盖（程序关闭太久）或重建时，才重新读一遍该盘的 MFT。U 盘等非 NTFS 磁盘仍用遍历目录 + ReadDirectoryChangesW。
- **读 MFT：几块同时在路上，空着的不读，任何簇大小都行。** 每次读 4 MB，同时有四次在路上：磁盘读后面几块时，这一块正在解析，磁盘不用停下来等（比两次快 9–16%，多占 8 MB 缓冲）。读之前先读 MFT 自己的占用位图（`$MFT` 的 `$BITMAP` 属性；大的 MFT 把它放在扩展记录里，0 号记录的属性列表指明在哪），整兆整兆空着的记录不读：删过大量文件、或者预先长大了的 MFT 里，这样的空段不少（本机 C 盘 4.4 GB 里有 1 GB）。两者合起来，C 盘的 MFT 从约 2.6 秒降到 1.3 秒。簇比文件记录小的分区（从 FAT32 转换来的、老分区常是 512 字节的簇；`format /L` 的 4 KB 记录配小簇）里，一条记录可能跨两个区段，读到的前半截先接到下一块的前面再解析。以前遇到这种分区就退回逐个文件夹遍历，在机械硬盘上要慢几十倍。
- **一块机械硬盘一次只读一个分区。** 几个盘同时读，但同一块机械硬盘上的分区一个接一个读：同时读两个，磁头会在两处来回跑。`IOCTL_STORAGE_QUERY_PROPERTY`（`StorageDeviceSeekPenaltyProperty`）问磁盘有没有寻道开销，`IOCTL_VOLUME_GET_VOLUME_DISK_EXTENTS` 问分区在哪块盘上；固态硬盘上的分区各读各的，问不出来的按机械硬盘算。建索引时状态栏写着正在读哪几个盘、读到百分之几（“正在读 D: 45%、E:”）。
- **快照压缩保存，半小时一次。** 快照每次都整个重写，所以它的大小就是写盘量。文件名只有约三分之一是不同的（index.js、__init__.py……），所以先把不同的名字各存一次，条目再按编号引用名字、按“往前数几项”记父文件夹；读的时候名字原样放进索引，不用再逐个查重，加载从 0.48 秒降到 0.26 秒。整个文件再按 1 MB 一块用 Windows 自带的压缩 API（XPRESS + 霍夫曼编码）分别压缩，每块带校验和；保存时几块同时在别的线程上压，加载时提前几块在别的线程上解。323 万项的快照从 92 MB 变成 27 MB，存一次约 0.26 秒。后来又把同类的东西放在一起，压缩器能找到更多重复：名字一个接一个、以 0 结尾；条目按列存，每 65536 个一组，先是这一组的“往前数几项”，再是标志，再是名字编号（第一次出现的名字记 0，因为它的编号就是下一个）；文件夹的 MFT 编号表按文件夹排序，两列都只记与前一个的差。快照因此 29 MB → 21 MB，加载 0.26 → 0.17 秒，保存时间不变。旧格式的快照照样能读。有改动时 30 分钟存一次：存过之后的改动下次启动时从变更日志补回来，存得勤只是多写盘；机械硬盘也因此能在 Windows 默认的空闲 20 分钟后停转。内容索引合并后留下的旧段文件要等快照不再引用它们才能删，攒到 32 MB 就提前存一次。
- **日志记录按顺序、可重复地应用。** 每一步都是“确保成某个状态”，所以从较早的位置重放也不会出错；改名的旧名和新名分成两条记录，保存的位置不会落在两者之间。日志只用文件夹的编号指明父文件夹，所以每个文件夹的 MFT 编号记在一张表里（约 40 万个文件夹占 5 MB 左右），随快照保存。
- **修改时间单独存一列，不放进条目里。** 每个文件和文件夹多 4 字节（1970 年起的秒数，用到 2106 年；0 表示不知道），和条目一样按 65536 个一块分配（`FileIndex::modified`）。按名字搜时所有线程都要把条目从头扫到尾，条目还是 20 字节，扫描不变慢；时间只有匹配上的才读。来源：读 MFT 时取 `$STANDARD_INFORMATION` 里的修改时间（本来就在解析这个属性）；变更日志里，新建和写入的记录用记录自己的时间，只往后推（重放旧记录不会把读 MFT 得到的新时间改旧），名字的增删顺带推进它所在文件夹的时间；时间被单独改过的（复制、解压会保留原文件的时间，记录带 `USN_REASON_BASIC_INFO_CHANGE`），等文件关闭的那条记录到了，出锁以后用 `GetFileAttributesEx` 读一次（不打开文件，不触发杀毒扫描，也不会下载云盘占位文件）；遍历目录时 `FILE_ID_BOTH_DIR_INFO` 本来就带时间。非 NTFS 盘只在新建、改名进来和重新遍历时更新时间（ReadDirectoryChangesW 不监视写入，免得缓冲区更容易溢出）。快照第 7 版每组条目多一列时间，记与前一项的差（相邻的文件常是一起写的）；本机 323 万项多了约 2 MB。读到第 6 版以前的快照时，照常马上可搜，同时把每个盘的 MFT 重读一遍补上时间，变更日志从快照记下的位置接着读，内容索引不受影响。
- **按名字搜，文件和文件夹各取前 N 名。** 以前取总的前 100 名，再把文件排到文件夹前面：名字完全一样的文件夹排在只沾一点边的文件后面，匹配的文件一多，文件夹就一个也进不了前 100。现在扫描时文件和文件夹各留一个最小堆（`NameSearchOptions::kindsApart`），只要文件夹时直接跳过文件（`foldersOnly`，“选择文件夹”对话框也用它，以前是从前 100 名里挑，可能一个都不剩）。排出来的顺序（`SearchEngine` 的 `arrange`）：最近打开过的几个，名字和输入完全一样的（`NameMatcher::isExactName`），然后两类分开，按设置文件在前或文件夹在前，各自按匹配程度；分数相同的，修改时间新的在前。按修改时间排时（`RankBy::Newest` / `RankBy::Oldest`，底栏的“最匹配 / 最新 / 最早”，Ctrl+S 轮换），堆直接以时间为键，取的是所有匹配项里最新（最早）的，不是把前 100 名重排一遍；这时不再把最近打开的提前，只标出来。最早在前时，不知道时间的（0）照样排最后（`timeKey`），否则一堆没有时间的会占满前面。默认是最匹配：按时间排只在“文件”“文件夹”里有，“全部”永远按匹配（应用、设置没有修改时间）。选了哪种会记住（`Results/Sort`，旧的 `Results/SortByModified=true` 读成 newest），但底栏一直亮着当前的选择，不会忘了自己换过。
- **不输入时：最近打开的，或最近修改的。** 底栏的“最近打开 / 最近修改”（Ctrl+S，设置里也有，`Results/StartList`）。最近修改的是 `newestFiles`：整个索引扫一遍，不用匹配名字，一页 256 个，滚到底接着取下一页（最近打开仍是 5 项），330 万项 256 个约 7 ms、1024 个约 45 ms，所以每次打开都现算，不缓存。各段先各留列表 4 倍（至少 80）个最新的，合起来后一批一批排序（`nth_element` 再排前一批），挑够就停：一次全排要 40 ms，挑出的一样。难的是挑出“人在做的”文件：直接按时间取，前几名全是编译输出、浏览器缓存、微信的数据库。所以跳过：系统、程序和工具文件夹里的（`LowPriority`，含 AppData、Temp）和隐藏的；工具写的名字（`isWorkFile`：点开头的、Office 的 `~$` 锁文件、下载到一半的、日志、数据库及其 -wal/-shm、崩溃转储、编译中间文件，还有以一长串十六进制开头的，程序拿哈希当文件名）；构建和环境文件夹里的一切（`OutputTrees`：文件夹里有 CMakeCache.txt、build.ninja、CACHEDIR.TAG（Cargo 的 target 等）、pyvenv.cfg，或名叫 CMakeFiles、obj），一次编译写几百个文件，否则全被它们占满。同一个文件夹最多取 2 个，同一棵目录树最多 3 个（启动器那个能滚动的列表里是 10 个和 30 个，翻多少页都一样，所以多取一页时前面的不变；`workTree`：用户文件夹里是“文档\某项目”这一层，别处是盘下第一层“F:\某项目”），一次导出几十张图、clone 一个仓库、或者解压一个把时间设成现在的大包（多层目录，每层都是新的），也留得下别的；`wsbench --newest --sim` 在真实索引上叠加这几种情况看前 5 个。比现在晚一天以上的不算（相机、别的电脑上的时钟错了）。在“文件夹”里，列的是这些文件所在的文件夹，每个一次，时间是其中最新文件的：文件夹自己的修改时间跟着里面任何增删变（程序的临时文件也算），而改写一个文件并不改它。在本机实测（`wsbench --newest`）前 5 个都是正在改的源文件和刚编好的程序。
- **数字键（Ctrl+1…9）在 Win顺 的搜索框在前面时先拿到。** 别的程序常把它们注册成全局快捷键（这台机器上 PixPin 占着 Ctrl+1–3，还有程序占着 Alt+1、Alt+2），Windows 把全局快捷键交给那个程序，前台窗口根本收不到。`NumberKeys` 是一个低级键盘钩子，只在启动器或对话框旁的搜索框是前台窗口时存在（窗口激活时装，失活时卸，线程是自己的），只拿“恰好按着这个修饰键”的 1–9：带 Shift、Win 的不拿，Ctrl 和 Alt 一起按的不拿（AltGr 打字），Alt 加小键盘不拿（Alt 码），输入法正在拼写时不拿。拿走的键用 vkE8 掩一下（同 KeyRouter），Ctrl 不会被当成单独按下（不会凑成双击 Ctrl），Alt 松开也不弹窗口菜单。钩子比全局快捷键先拿到键，后装的钩子又排在先装的前面，所以 AutoHotkey、Listary 的钩子也挡不住它（实测：测试程序自己注册 Ctrl+5 当“别人的快捷键”，搜索框在前面时按 Ctrl+5 打开了第 5 行，那个热键一次也没收到）。序号从看得见的第一行数起（至少露出一半的行），按住 Alt 马上显示，按住 Ctrl 0.5 秒才显示（Ctrl 还用于 Ctrl+C、Ctrl+Enter、Ctrl+点击和双击 Ctrl）。刚打完字、结果还是上一个查询的时候按下的数字或 Enter，等新结果出来再执行（`holdUntilShown`），接着打字就作废。设置页用 `RegisterHotKey` 逐个试这 9 个组合，被占用的写出来；用钩子收键的程序试不出来。剪贴板的数字键另有一项设置，默认还是 Alt（已经发布过，而且剪贴板里按住 Ctrl 是多选）。
- **内容索引：少打开文件。** 内容搜索慢在打开文件：Windows Defender 在每个文件第一次被打开时扫描它，每个要好几毫秒，而且过一会儿就忘了扫过，下次搜索又要扫；读和匹配本身几乎不花时间。所以与其让读文件更快，不如少打开文件：索引记下每个文件里出现过哪些中日韩字和相邻两字，以及哪些“三个连在一起的 ASCII 字符”（字母不分大小写，空格和标点也算，连着的空白算一个空格）。搜一两个中日韩字时它就是答案；搜更长的词时，文件必须含有词里的每个片段才可能含有这个词，候选因此筛到很少，只打开这些文件取行号和摘要。索引的文档表随快照保存，和文件名索引永远对得上；NTFS 变更日志里的“内容被改写”记录告诉它该重读哪个文件。日志断了（程序关太久）时，只比较文件大小和修改时间，变了的才重读。新读的文件先在内存里攒着，攒够约 8 MB 写成一个段文件；同一级的段文件攒满 8 个就合成一个上一级的，所以每个片段只被重写几次，合并时边读边写，不会一下占很多内存。段文件尽量紧凑，靠三件事。一是**同样的内容只记一次**：片段完全相同的文件（一个文件的几份拷贝、一个项目的几份检出、几个版本的 Qt 带的同样的头文件）共用一份“内容”，倒排表里记的是内容号，文档表里每个文件记它的内容号；认相同靠片段集合 SHA-256 的前 96 位（`grams::fingerprint`，`BCryptHash`），写在段文件里，新读的文件先查一遍。作者电脑上 33 万个文件只有 14 万份不同的内容。二是**相似的内容编号挨在一起**：整体合并（`ContentIndex::merge`）先把所有倒排表过一遍，按每份内容里各片段打散后的最小值（MinHash）、再按片段数给内容重新编号；片段大都相同的内容多半有同一个最小值，于是落在一起，一个片段的内容号列表就成了一段段挨着的号。三是**内容号列表用二分插值编码**（Moffat 和 Stuiver）：先写中间那个号，只用剩下可能的取值所需的位数，再这样写左右两半；挨着的号几乎不占位，一整段连号一位都不用。四个以内的短列表直接写在片段目录里。片段目录只记与前一个的差，每 64 个留一个可二分查找的入口。33 万个文件因此从 172 MB 降到 50 MB（后来片段带上空格和标点，涨到 91 MB），查一次索引仍是几毫秒，`wsbench --content-index --verify` 筛掉的文件里一个含有的都没有。MinHash 排好之后，再用递归图二分（Dhulipala 等，2016）细排：把内容切成两半，在两半之间交换内容，只要交换后各片段的内容更集中（按内容号间隔所需的位数估算）就换，然后两半各自再这样切，切到几十份为止。拿全部片段来做要把倒排表整个转置一遍，近 800 MB 内存、18 秒；只用“很多内容都有的片段”里按哈希抽出的约 1/32（约 600 万对，24 MB），效果几乎一样（倒排表 79 MB → 59 MB，全部片段是 57 MB），16 个线程约半秒，结果和线程数无关。四个以内的短列表多是中文的两字片段，又多半出自少数几份长文档：按 MinHash 编号时这几份恰好号小，一两个字节就记下，二分之后号散开了要三个字节。所以段文件里另存一张表，列出短列表用到的内容，按用到的次数排，短列表记的是在这张表里的位置（4.3 MB，直接记号要 9.4 MB）。合起来 94 MB → 75 MB。换了格式后第一次启动，旧的内容索引读不了，会在后台重建一遍。
- **片段带上空格和标点：一行代码也筛得准。** 起初只记单词内部的三字片段（`con`、`aut`、`loc`），一行代码 `const auto lock = index->readLock();` 拆出来全是最常见的片段，33 万个文件里有 1392 个“可能含有”（共 1 GB，其中 686 MB 是几十 MB 的导出 JSON），实际只有 12 个；没被 Defender 扫过时 2.7 秒才出第一条、6.5 秒才读完。代码靠空格和标点区分（`o l`、`->r`、`();`），把它们也算进片段后只剩 13 个，`for (int i = 0; i < n; ++i)` 从 15.5 万个降到 148 个。代价是索引从 50 MB 涨到 91 MB（每个文件的片段多了约 77%）。试过把所有标点算成一类：71 MB，但同样几行代码要读的文件多十倍（125、881、3449 个），没用。连着的空白（空格、Tab、换行）算一个空格，所以缩进和换行方式不同不会被误排除；最后仍逐字核对，不会多出结果。片段编号的格式变了，升级后第一次启动在后台重建一遍。
- **建内容索引时不让线程互相等。** 关掉 Defender 实时保护量第一次建立（`wsbench --service --content`），剩下的全是自己的开销，75 秒里有四处在排队，改完是 27 秒，再改完后面几条是 21 秒；开着 Defender 时这几处一样省（详见 pitfalls 的“内容索引”）。一是**写段文件不锁着**：内存攒够一个段时，整块交出去（`m_writing`），内存另起一块接着收；排序、编码、写盘都在锁外，这批片段在新段装上之前搜索和查重照样找得到。以前锁着写，读线程每次都一起停下，第一次建立累计 12 秒；后来在锁里复制一份再写，每个段又让 16 个线程一起等 2 毫秒。排序是只按片段排的基数排序（内容号本来就是递增的，稳定排序后自然有序），先按抽样出的片段把这批切成几十段，各段在几个线程上各自排、各自编码，再按顺序写：一个段从 42 ms 降到约 15 ms。排序和编码用的缓冲区留给下一个段：新申请的大块内存每 4 KB 一次缺页，比排序本身还慢；每次新建、用完就放的编码缓冲又会留在进程里，合并完常驻多出 20 MB。写得赶不上读时，攒过一个段的量就等一等。查一个文件的片段以前有没有出现过（查重）放在共享锁下做，独占锁里只补查这期间新来的：以前它占了独占锁八成的时间，16 个线程等锁比哈希和入库本身还久。交给索引的时间每个文件从 108–188 µs 降到约 60 µs。二是**小段合并时不停读**：8 个小段合成一个时，段里的内容号全都保留（没人用的留给整体合并去扔），所以新加的文件不会用到被扔掉的号，读线程不必停；以前每次合并都要等手上的文件（常常是几秒一个的 PDF）读完，累计 13.6 秒。三是**整体合并按片段范围分给多个线程**：每段各自解码、重新编号、编码，写的时候按顺序拼起来，结果和单线程逐字节相同；33 万个文件 13 秒 → 1–1.5 秒。按多少切不能看字节：几乎每个文件都有的片段，编码后几乎不占字节，解码却最费时，所以按每个片段有几份内容来估。四是**文档提取进程不用后台模式**：建索引时每个文档 93 ms → 25 ms。另外切片段时把连着的 ASCII 放在一个用局部变量的循环里，UTF-8 检查一次跳 8 个 ASCII 字节，多字节字符整个在缓冲区里时直接解码，切片段快了约一成（`wsbench --content-index --grams-only`）。
- **文档的副本只读一次。** 本机 5815 个文档里 2628 个和另一个逐字节相同（微信把同一个文件存成“x.pdf”“x(1).pdf”，还有整个拷过去的备份文件夹），按字节算占四成，读的时间也差不多占四成。文件索引不记大小，所以读文档前先取一下大小（属性，不打开文件）；之前读过同样大小的文档，才把两边的内容整个算一遍 SHA-256 比较（读文件只是读出文字所花时间的零头），相同就把原件的文档整个给它（`ContentIndex::addCopy`：同一份片段、同一份文字），不再交给 WinShunExtract.exe。原件还在读时，副本等它读完；只等排在自己前面的，所以不会互相等。原件被改过（大小和修改时间对不上）就不算。另外，文字相同的文档（包括字节不同、文字相同的）在 `.texts` 里只存一份，按压缩后文字的 SHA-256 认；引用它的文档都没了才算垃圾，整理时每份只拷一次。
- **搜索读过的文件也进索引。** 索引还没收录的文件（刚装好、升级后重建中，或刚被改过），内容搜索只好自己打开来读；以前读完就扔，关掉窗口再搜一次又全读一遍。现在这些文件整个读完（找到那一行后把剩下的也读完），片段直接交给内容索引（`ContentIndexer::Intake`），文档连同读出的文字一起交，和后台建索引读到的一样：下次搜索，不管搜什么，都不用再打开它们。条件和后台建索引相同：文件名索引已建完、内容索引开着且没在搬家、文件在跟踪变更日志的 NTFS 盘上；读的过程中文件被改了，记下的那份算作过时。搜索结束后叫醒后台建索引，合并新写的段文件，接着读剩下的。
- **大小上限按文件种类分。** 一个上限管所有文件不合适：手写的代码很少超过几 MB，几十 MB 的 `.js` 多是打包压缩的脚本，几十 MB 的 `.json` 多是导出的数据；它们几乎含有所有片段，每次搜索都在“可能含有”里，要整个读一遍。所以分四类：文本和日志（以及没列出的扩展名）64 MB，源代码 8 MB，数据和网页 16 MB，文档 512 MB（几十上百 MB 的 PDF 和演示文稿大多是图片，读出的文字另有每个 16 MB 的上限），设置里分别可改。以前改过总上限的，另两类先沿用那个值。参考 SharePoint：一般文件 150 MB，PDF 和 Office 文档放宽到 512 MB（解析出的文字另有 200 万字的上限）；Recoll 纯文本默认 20 MB。
- **“全部”里的内容搜索照原样找。** 以前“全部”把输入里的引号去掉、遇到 `*` `?` `!` 就不搜内容（它们在文件名搜索里是通配符和排除），所以 `printf("hello")`、`if (!ok)`、`char* p = s;` 这样的代码在“全部”里找不到，切到“内容”才找得到。现在“全部”把输入原样交给内容搜索，和“内容”一样由 `contentTerms` 处理：像代码的一行整行照原样找（整行套一对引号时去掉这对引号），其余按词分开、引号里是一个短语。看着是文件名语法（`*.log`、`report !draft`、`ext:`）又不像代码（没有 `=` `;` `(` `)` `{` `}` `<` `>` `[` `]` `->` `::` `&&` `||`）的，仍只搜文件名。
- **多个词：文件名里没有的，可以在上级文件夹名里。** 以前每个词都得在名字里，`src app`、`电脑便捷 readme` 这样“一个词说在哪、一个词说叫什么”的输入什么也找不到。现在有两个以上的条件（词，或词加 `ext:`）时，普通的词（不是通配符，不带 `\`）在名字里找不到，就去它所在的各级文件夹名里找（也认拼音），每个这样的词只加 3 分，低于名字里任何位置，所以名字里都有的排在前面；但至少要有一个词（或扩展名）落在名字里，否则一个“工作”文件夹下的几万个文件会全被列出来。只有一个词时照旧只看名字。每个文件夹含哪些词按搜索记在一张 1024 格的表里（`NameMatcher::Folders`，每个切片一张，同一文件夹下的文件挨着），一路往上算到记过的那级为止，所以每个文件夹基本只看一次。代价是第一个词不在名字里时不能立刻排除，得把其他词也查一遍：327 万项两个词约 14–18 ms（以前约 8–10 ms），一个词不变。
- **文件名搜索先看不同的名字，再看每一项。** 329 万项只有约 101 万个不同的名字（重复的只存一份）。搜索先把名字池里的每个名字过一遍（`NameMatcher::nameMayMatch`，按 256 KB 的名字块分给各线程），可能命中的在一张位图里记一位（每 3 字节一位：一条名字记录至少 3 字节；`NameBits`，每个线程留一张重复用），再看各项时先查这一位，没记的直接跳过，只有记了的才完整地匹配（上级文件夹、`!` 排除、文件夹条件）。名字以外的条件在第一遍里一律放宽（当作文件、上级文件夹的词都算有），所以只会多放过、不会漏。结果和逐项匹配完全一样（`wsbench --check`）。每项也从 20 字节减到 17 字节（扩展名长度和“含汉字”挪到名字记录前面，每个名字只存一次）。加上线程池从 8 个线程放宽到 16 个：常见查询从约 10 毫秒降到 2–3 毫秒，单字母 18 → 11 毫秒，加载 190 → 150 毫秒，文件名索引少约 6 MB。代价是内容搜索筛候选时要到名字记录里读扩展名长度，单线程多约 3 毫秒（并行后约 0.2 毫秒）。
- **内容搜索多个词：都在文件里就算，不必挨着。** 以前整串输入（连空格）当一个短语找，`报告 2025` 只找“报告 2025”连在一起的，几乎总是零结果。现在按空格分词（引号里是一个短语），文件里每个词都出现才算；像代码的一行（`looksLikeCode`：含 `=` `;` `(` `)` 等）仍整行照原样找，引号、空格都不动（`contentTerms`）。内容索引取各词片段的并集来筛，文件必须有全部片段才可能含有每个词。`ContentScanner` 对每个词各编一份 UTF-8/UTF-16/ANSI 的字节查找器：每个窗口先找还没见过的词各自第一次出现的行（解码核对，顺带记下这一行含哪几个词）；全都见过就是命中，再在这个窗口里找含词更多、或更多词在词首的一行（最多再看 64 处），同样好取靠前的。有一个词写不进文件的本地代码页就不可能命中。摘要从能放下最多个词的那一处前一点开始（不一定是第一个词），所有词都高亮（`SearchResult::snippetMatches`）。
- **内容结果按相关度排，不按读到的先后。** 以前先读完的先列，`拼音 汉字 搜索` 排在前面的是什么词都有的词典，`TODO fix` 前面全是打包的 bundle.js（`fix` 在 `prefix` 里）。现在每条命中打一个分（`contentRelevance`）：几个词在显示的那一行里都有 +40（只有部分按比例）；词在词首（`fix`、`fixed`，不算 `prefix`；中文词总算，`readLock` 里的 `Lock` 也算）最多 +20；文件名里有这些词最多 +30；在你自己的文件夹 +15、隐藏 −5、系统和程序文件夹 −10；一周内改过 +12、一月内 +8、一年内 +4；显示的那一行总长 8 KB 以上（压缩的 js、一行的 json/html；只解码匹配前后 600 字节，但 600 字节才 200 个汉字，普通段落常超过，所以往外多看原始字节找换行，量整行）−35，而且不算“同一行”。引擎每批先按分排好再发，启动器把新来的插到内容结果里分数比它低的前面；但不插到键盘所在那一行及以上（`Launcher::currentRow`，由 Main.qml 报），看着的、正要选的不会被挤走；还在第一行时更好的可以顶上去，第一行仍是当前行（`betterFirstRow`）。只排已经读到的：一页 256 条，读完前后来的更好的会插进来。
- **完整路径整个当一个词。** 搜索词按空格分开、要全部命中，所以粘贴进来的 `C:\Users\me\Documents\Tencent Files\…\emoji` 被拆成“在 Documents 下、名字含 Tencent”和“名字含 emoji”两个条件，同一个名字不可能都满足，一条也找不到。现在整个输入是盘符或共享开头的路径时（`pathtext::splitTyped` 认得出，`%变量%`、引号、`file:` 也照它的规矩），`parseQuery` 把它当成一个词。结果分两段：先是那个文件夹里名字匹配的（从磁盘列，同文件对话框旁的搜索框一样，`listTyped`；名字和输入完全一样的在最前，只输到 `\` 时文件夹自己在最前，接着是里面的全部），再是索引里更深处名字匹配的，用 `findPath` 找到那个文件夹、只留真在它下面的（路径里的文件夹名按“包含”匹配，不过滤会混进别处的）。路径不搜文件内容，也不列应用、系统入口和网站。路径后面跟 `ext:`、通配符时不算路径，照旧按词分开（`D:\Projects\ ext:pdf`）。
- **从中间写起的路径，回车就进去。** `tools/screenshots/work/out/covers/` 按词的规矩是“名字随意、上级依次含 tools……covers”，列出来的是 covers 里面的东西，covers 自己不在其中，回车打开的是第一张图片。用户写的是路径，意思是去那里。现在整个输入是不带盘符的路径时（`pathtext::splitRelative`：含 `/` 或 `\`，每一段都是合法的名字，不以 `!` 开头，没有 `*` `?`，段首段尾没有空格，所以 `covers/ png` 仍是两个词），`findRelativePath` 在索引里找名字一字不差（ASCII 不分大小写，同 NTFS）、上面几级也一字不差且一级接一级的条目；以分隔符结尾时只要文件夹。找到的最多 3 个放在第一行起（最近打开过的、不在系统/程序目录也不隐藏的、层级浅的在前），下面照常是搜索结果，去掉重复的。没找到（还没输完：`tools/scr`）就和以前一样。只比较名字长度和名字本身，327 万项扫一遍不到 1 ms（`wsbench "tools/out/covers/"` 会打印）。对话框旁的搜索框走同一个 `SearchEngine`，回车同样转到那个文件夹。
- **文档在单独的、受限的进程里读。** Win顺 以管理员身份运行，文档解析代码又大又复杂（PDFium 连同它带的 FreeType、OpenJPEG 等），文件却可能是别人发来的。所以主程序不碰文档内容：`WinShunExtract.exe` 由 `CreateRestrictedToken` 去掉管理员组和特权、再降到低完整性级别后启动，放进一个作业对象（单个进程最多 2 GB 内存、不许再开进程、不许碰剪贴板和别的程序的窗口、Win顺 退出它就结束），并打开堆损坏即终止、禁止动态生成代码、不加载远程和低完整性的 DLL 等缓解措施。它自己不打开任何文件，每个请求带着主程序复制过去的只读句柄。崩溃、超时（按文件大小 20 秒到 3 分钟）或超出内存时只丢这一个文件，换一个新进程接着读。读出的文字（UTF-8，每行记着在第几页 / 幻灯片 / 表的第几行）压缩后存进内容索引旁的 `.texts` 文件：搜索时从这里取摘要和位置，不用再读一遍文档，也就不再等 Defender 扫描文档。文档的格式看开头的字节，不看扩展名：`.wps` 可能是 Word 97 也可能是 docx，网页系统导出的 `.xls` 常常是 HTML 表格。
- **系统入口用 Windows 自己的设置检索清单。** 开始菜单搜设置靠的是 `%WINDIR%\ImmersiveControlPanel\Settings\AllSystemSettings_*.xml`：约 1500 条，每条有名称和几组关键词，都是资源字符串，`SHLoadIndirectString` 按显示语言解析（中文的关键词里也带英文和常见拼错，“查看网络连接”的有“适配器;卡;adapters;adaptor”）。几份清单对应不同版本的“设置”，以条目最多的为准。控制面板的条目直接给出打开方式（`shell:::{…}`、`Microsoft.DeviceManager`、命令行）；新版“设置”的页面只记页面 ID（`SettingsPageNetworkEthernet`），`ms-settings:` 地址要从较旧那份清单的 `PolicyIds` 里找。那是按字母排的一串名字，第一个不一定是页面本身（“声音”的第一个是 `apps-volume`），所以取页面 ID 里写着的那个（`installed-apps`），否则取被其余名字当前缀的那个（`sound` 之于 `sound-devices`）。带 `shcond://` 条件的条目（只在服务器上、要有触控笔、家庭版没有……）按注册表和系统信息判断，判断不了的不显示。Windows 安全中心的条目名称只解析得出英文，不用它们，改由 places.txt 写中文名。
  - 清单的关键词偏书面，“网卡”“梯子”这类说法没有，`src/core/places.txt` 补上（加在页面本身那一条上，不加在页面里的各个任务上，否则“壁纸”会显示成“视差背景”），也加开始菜单里没有的工具和文件夹。`wsbench --places [词 …]` 列出本机所有入口或每个词的前几名，并报告 places.txt 里对不上任何入口的条目。
  - 排序：places.txt 的关键词完整命中（50 分）高于名称以这个词开头（30 分加覆盖比例），Windows 的关键词完整命中（30 分）高于偶然对上的拼音首字母（`dns` 对上“电脑设置”）。只有一个字时只看名称。反过来，只靠拼音首字母对上关键词的（`glq` 对上“隔离区”）排在名称被这个词占了一半以上的入口之后（“凭据管理器”）：首字母容易撞上，关键词又不显示，用户看不出为什么是它；名称里只沾到一点的（`wk` 里的“当我看向别处时”）不算，“网卡”照样排第一。同一个打开命令只出一行（一个页面里的几个任务都打开这个页面），**全部** 范围里最多列 5 个，和应用按分数排在一起。
  - 读一遍约 0.3–0.5 秒，在后台；每次打开搜索框时比较清单文件的时间和显示语言，变了才重读。打开时和应用一样交给资源管理器，以普通权限运行。
- **结果拖出去：和资源管理器给的一样，只复制不移动。** 文件和文件夹的行用鼠标按住、拖过系统的拖动距离（`styleHints.startDragDistance`，即 `SM_CXDRAG`），就把它拖出窗口（`Launcher::dragOut` → `dragout::drag`）；它在多选里时拖整个多选。应用、系统入口、网页、插件的行和离线共享上的不拖，按住拖动照旧滚动列表；文件行上鼠标拖动不再滚动列表（`preventStealing`，只对鼠标：触摸照样滚），滚轮、滚动条照常。
  - 数据对象是外壳自己的（`SHCreateDataObject`，父级是桌面，每项是完整的 ID 列表，不同文件夹的结果能放在一起），资源管理器、聊天、邮件读得懂的都有；它不为这种对象生成 `CF_HDROP`，自己写进去，再写 `Preferred DropEffect = 复制`。`SHDoDragDrop` 只允许复制和快捷方式：同一块盘上拖进文件夹时资源管理器默认是移动，会把用户的文件挪走。拖动图像是外壳给的（缩略图，多项带数字）。
  - Win顺 以管理员运行，目标程序不是：实测（2026-10-11）不受 UIPI 影响。OLE 往下调用目标的 `IDropTarget`，目标回调 Win顺 的 `IDataObject::GetData` 也放行（不用 `CoInitializeSecurity`）；只认 `WM_DROPFILES` 的老程序也收到。资源管理器（同盘，复制）、`RegisterDragDrop` 和 `DragAcceptFiles` 的普通权限测试窗口都收到完整路径（含空格、中文，多项）。
  - `SHDoDragDrop` 是模态循环，期间启动器不失去激活，不会收起。放下后不主动收：资源管理器接住后自己拿走焦点，启动器就因失去焦点收起（实测）；不拿焦点的目标，用户点过去时照常收起。OLE 的循环吃掉了松开按钮的消息，Qt 还当按着：拖完给窗口补一个 `WM_LBUTTONUP`，`ResultRow` 也记着这次是拖出去的，那次“单击”不打开文件。共享连不上时先问一下服务器（最多 1.5 秒，和打开一样），免得外壳解析路径卡住界面。
- **网页搜索：关键词打头才算，文件照常列在下面。** 只在“全部”里：输入以某个关键词开头（`gh`，或 `gh WinShun`），那个网站或这次搜索就排在第一行，回车打开；下面照常列出应用和文件，关键词和文件名撞上也不碍事，按一下 ↓ 就行。只有关键词、没有 %s 的网站不接文字，`blog 笔记` 仍是普通搜索。关键词打头时不再在“全部”里搜文件内容：这是要去网上搜，读文件只是白花时间。不输关键词时按名称（含拼音）也能找到网站，比同样匹配的应用低 5 分：应用在这台电脑上。
  - 要搜的文字按 UTF-8 百分号编码（空格是 `%20`，`/`、`&` 也编码），原样放进 `%s`，引号也不动，网站自己认 `"整个短语"`。主页不填时取搜索网址的 `https://网站/`；应用自己的链接（`obsidian://search?query=%s`）则是去掉 `%s` 的那条链接。
  - 设置里填网址时：没写 `https://` 的补上；只有 `%25s` 没有 `%s` 的换回 `%s`，所以“在网站上搜 `%s`，再复制地址栏”就能得到搜索网址。不接受 `file:`：要搜的文字落进文件路径里，可能打开一个程序。
  - 打开和别的一样交给资源管理器，以普通权限运行。搜过什么不记进最近使用。
  - 自带 10 个中文网站常用的（百度、必应、哔哩哔哩、知乎、微博、抖音、小红书、淘宝、京东、百度翻译）。关键词用整词（`baidu`、`jingdong`），不用两个字母：两个字母常是文件名的开头，打 `bd` 找文件时不该先冒出一个网站；按名称和拼音首字母（`bd`、`jd`）照样找得到它们，只是不置顶。也避开随包插件 winshun.web 的关键词（bd gh yt wiki bing bili）。
- **网页搜索的行显示网站自己的图标**（浏览器地址栏左边那个），第一次显示时从网上取一次，存在 `%LOCALAPPDATA%\WinShun\icons\web\<主机名>.png`，30 天后再取；没取到之前和取不到时用默认浏览器的图标（`AssocQueryString(ASSOCF_IS_PROTOCOL, ASSOCSTR_EXECUTABLE)`）。按主页的主机名存（`fanyi.baidu.com` 和 `www.baidu.com` 各一个）。用户也可以给某个网站换一张自己的图（设置里“选择图片…”，PNG 或 ICO，和网站图标一样只用 Qt 自己的解码器读）：整理成至多 256 像素的方形 PNG，按内容的 SHA-1 前 16 位命名存进 `icons\web\custom\`，`[WebSearch]` 里只记文件名（读设置时只认这种名字，不认路径）；行的图标地址是 `custom:<名字>`（`WebShortcut::iconRef`），没人用的图在保存、移除、导入后删掉。导入导出是一个 JSON 文件（`format: winshun-web-shortcuts`），自选图标以 `data:image/png;base64` 写在里面；导入时按关键词合并，已有的原位替换（文件里没有图标就保留原来的图），新的排在后面，用不了的条目跳过并报个数。
  - 只在行或设置里的那一项要显示时才取，不在启动时把所有网站取一遍：用户没用过的网站不去连。取不到的这次运行里不再试。一条后台线程依次取（WinHTTP，走系统代理，10 秒超时），取到后行的图标地址从 `web/https` 换成 `site/<主机>/<主题>`，列表只刷新那几行。
  - 取哪个：读主页（前 2 MB），按 `<link rel="icon">` 里标了 64 px 以上的、其他 icon、`/favicon.ico` 的顺序，取到 64 px 就停，最多问 5 个地址；都只有 16 px 或没有时才用 apple-touch-icon（给手机桌面的，清楚但常是另一张图：B 站的带“WEB”字样）。实测 11 个网站都是浏览器那张：百度 64、淘宝 64、京东 96，其余 32（2026-10）。主页被重定向到登录或验证页时，也试原网站的 `/favicon.ico`。
  - 解码不用 WIC：Win顺 以管理员运行，WIC 会加载装在机器上的任何解码器，而这是网上来的字节。PNG 用 Qt 自带的读取器，ICO 自己读（PNG 帧，或 1/4/8/24/32 位位图加透明掩码，处处查边界），只认这两种；超过 1 MB 或 1024 px 的不要。存盘前缩到 128 px 以内、补成正方形，先写 `.part` 再改名。SVG 不取。
  - 画法（`siteicon::drawn`）：四边各缩进 1/16；铺满到角的方块（apple-touch-icon 那种）圆角半径为边长 1/5，用图片当画刷填圆角矩形（裁剪的边不抗锯齿）。几乎整个都和行的底色贴近的（90% 以上的像素 RGB 距离 < 64：GitHub 的黑猫在深色主题下）垫一块另一主题颜色的圆角底板，图缩到 3/4；抖音的黑方块（68%）、百度的白方块（63%）靠上面的图案就看得见，不垫。所以图标地址带主题，换主题时行会重新取图。
  - `wsbench --site-icon <主页>… [--save 文件夹]` 按程序的方式取一次，列出问过的地址和结果，存下保存的图和 32/48/64 px 浅色、深色下画出来的样子。
- **收藏夹：一份文件，启动器和对话框共用。** 收藏（`Favorites`）可以是文件夹、文件、应用或系统入口，存在 `%LOCALAPPDATA%\WinShun\favorites.json`（`{"format": "winshun-favorites", "version": 1, "favorites": [{kind, path, name, keyword}]}`，导出的也是这个格式），不放进 INI：“恢复默认设置”会整个换掉 `Settings`，收藏不该跟着没了。每次改动用 `QSaveFile` 整个写一遍；读不了的文件改名成 `favorites.json.bad` 留着，不被下一次改动覆盖；更新的版本写的（version 更大）这次只读不写。对话框搜索框原来“固定”的文件夹（`dialog-pins.txt`）第一次启动时搬进来，旧文件改名成 `.migrated`。
  - 什么都不输入时（最近打开、最近修改都一样）收藏排在最前，按用户排的顺序、按当前范围筛（“文件”列文件和文件夹，“文件夹”只列文件夹，“内容”不列），后面的最近项目不再重复。查它们还在不在，不放在按键的路上：搜索线程上和最近打开的项目一样交给每个盘一条线程去问（`RecentOnDisk::look`，最多等 100 毫秒），磁盘明确回答“没有”（`ERROR_FILE_NOT_FOUND` / `ERROR_PATH_NOT_FOUND`）才标“已不存在”（调暗，右键可以移除）；问不到的（服务器没回答、共享名不对、没有权限、盘没醒）照常显示，已知离线的共享根本不问。
  - 输入时：收藏的行标“收藏”（有关键词的标“收藏 · gz”），匹配的前 5 个提到最前，索引里没有的（被排除的文件夹里的）到磁盘上问；只输入一个收藏的关键词（不分大小写），它排第一、算 `exact`，分数和网页关键词一样，插件的行压不过它，回车就打开；按时间排序、输入了路径时只标记、不提前。关键词和网页搜索、插件共用：网页 > 收藏 > 插件。设置里保存时互相拒绝；导入网页搜索列表时撞了收藏关键词的照样导入（输入时网页在前），结果里说“N 个和收藏的关键词重复”；插件的关键词被收藏占了，设置页的冲突写“收藏‘名字’”。
  - 收藏的文件夹按 `Tab` 进去接着搜（底栏提示“进入文件夹”）。设置 → 收藏夹（`FavoritesSettings` + `FavoritesSection.qml`）：拖把手排序（`上移`、`下移` 给键盘）、改名称和关键词、选或拖进来添加、导入导出；“已不存在”在后台线程上查，本机盘的先显示，网络上的先探一下服务器（`share::reachable`）再问；和启动器一样，只有“找不到文件 / 路径”才算不在，服务器不通、没有权限都照常显示。从资源管理器拖进来走 `WM_DROPFILES`（`FileDropTarget`：提权的窗口收不到普通权限进程的 OLE 拖放，见 pitfalls）。导入时已经有的那一项，缺关键词就补上（没被占用的话），名字还是它自己的就换成文件里的。
- **窗口预先画好一次。** 窗口第一次显示时要建立显卡绘图环境、着色器和字形缓存，之后隐藏也一直保留，所以只有第一次打开慢。启动 1 秒后先在隐身、不抢焦点的状态下画一帧再藏起来，第一次打开就和之后一样快。代价是一启动就多占这部分内存（约 20 MB 内存和 10 MB 显存），反正打开过一次后也会占着。
- **打开的文件仍是普通权限。** 管理员进程直接打开文件，被打开的程序也会带管理员权限，不安全；所以“打开”交给资源管理器代为启动（它桌面的 `ShellExecute`；桌面从 `ShellWindows` 里掉了时借任意一个文件夹窗口的），只有 `Ctrl+Shift+Enter`（以管理员身份运行）才提权。一个资源管理器窗口都找不到时（别的桌面外壳，或资源管理器出了问题），用桌面外壳的令牌启动：文件夹、应用、系统位置、链接交给新的 `explorer.exe`，文件和带参数的命令交给 `rundll32`（见 pitfalls.md）。资源管理器正在重启时会等几秒再试；都不行就不打开（托盘会提示），绝不悄悄提权。
- **开机自启用计划任务。** Windows 会跳过启动项（注册表 Run 键）里需要提权的程序，所以改为登录时以最高权限运行的计划任务“WinShun”，开机不弹 UAC。旧版本写在 Run 键里的设置会在启动时自动迁移。
- **对话框里的 Ctrl+G 和搜索框只靠窗口消息。** Listary 把钩子 DLL 注入其他程序，在对话框进程里直接让它换文件夹；一个以管理员身份运行的程序往别的进程里注 DLL，正是杀毒软件盯的行为，注进去的代码出错还会拖垮别人的程序。Win顺 从外面像用户一样操作对话框：
  - **只在文件对话框在最前面时注册 `Ctrl+G`。** `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)` 跟着前台窗口走：前台是文件对话框（`#32770`，里面有 `DUIViewWndClassName` 和地址栏，或者是 XP 风格的 `SHELLDLL_DefView` 加文件名框）就 `RegisterHotKey`，换走就注销。别的程序里 `Ctrl+G` 照旧，也用不着键盘钩子。收到事件时看的是当时真正的前台窗口（`GetForegroundWindow()`），不是事件里说的那个：资源管理器被别的程序换了文件夹时，会自称到了前台（见 pitfalls.md）。对话框刚到前台时控件可能还没建全，所以 `#32770` 窗口在 0.5 秒内再看几次。对话框在前台期间，再用一个只挂在它线程上的钩子听它的显示、隐藏和移动（`EVENT_OBJECT_SHOW` 到 `EVENT_OBJECT_LOCATIONCHANGE`），搜索框据此出现、跟随、隐藏：对话框往往先到前台，过一阵才显示出来。
  - **找文件夹**：`IShellWindows` 列出资源管理器的每个标签页，各取 `IShellBrowser` 的窗口和当前文件夹（`SIGDN_FILESYSPATH`）；再按 `EnumWindows` 的前后顺序找最前面的资源管理器窗口，取它排在最前的 `ShellTabWindowClass`（正在显示的标签）。显示的不是磁盘上的文件夹（主页、此电脑、搜索）就看下一个窗口。
  - **让对话框换文件夹**：往地址栏的输入框里 `WM_SETTEXT` 填入路径，再发回车，和在资源管理器里一样。这个输入框第一次要靠在面包屑最右边的空白处投递一次单击才会建出来，之后一直在（不用时隐藏），直接往里填就行，不再依赖单击：实测出现过投递的单击不起作用，原因没查到（见 pitfalls.md）。换好以后把焦点还给原来的控件（通常是文件名框，`WM_NEXTDLGCTL`），但只在对话框还在前台时：用户已经去了别处（比如点进了搜索框），就不再动它。地址栏显示的已经是目标文件夹就不动。平时不往文件名框里填文件夹再按“确定”：选择文件夹的对话框会直接选中它并关闭。XP 风格的对话框没有地址栏，只能用文件名框：路径末尾加 `\`，另存为对话框就不会把它当成文件名（文件夹不存在时只报错），跳过去后再把原来的文件名填回去；新式的打开、另存为对话框在地址栏不听使唤时（单击没建出输入框）也这样做，日志里记一条警告。选择文件夹的对话框没有这条退路。
  - **搜索框**（`DialogBar`）是 Win顺 自己的一个窗口，显示时不抢对话框的焦点（`_q_showWithoutActivating`），贴在对话框可见边框（`DWMWA_EXTENDED_FRAME_BOUNDS`）外 4 逻辑像素：在下方时和对话框一样宽，在左右两边时宽 480、和对话框顶边对齐（列表在下面放不下时整体往上提）。放在哪边由设置决定：“自动”按下方、右边、左边的顺序取第一个放得下的（搜索框连同 5 行列表）；已经在某一边、那边还放得下就不换，对话框拖来拖去时不会来回跳；选定一边的，那边放不下时按“自动”的顺序另找一边。都放不下时放在下方，列表往上展开，下方没地方就放到对话框上面。它是置顶窗口：对话框在前台时 Win顺 没有前台权限，`SetWindowPos(HWND_TOP)` 不起作用，搜索框会被资源管理器之类的窗口挡住；它只在对话框或它自己在前台时显示，置顶不会挡着别的程序。点进搜索框时，列表等这次单击松开才打开：列表往上展开会把输入框往下挪，单击就落到了第一行上。列表最多 5 行。
  - **给搜索框腾地方**：对话框第一次显示时，如果搜索框和整个列表哪边都放不下（“自动”），或者选定的那边放不下，就用 `SetWindowPos` 把对话框调小：放下方就调矮，顶边不动，矮到 400 逻辑像素还放不下再往上挪；放左右两边就调窄，另一边的边不动，窄到 640 逻辑像素还放不下再往另一边挪。三种情况是同一个算法（`roomAlong`，左边按坐标取负）。“自动”时只要有一边放得下就不动对话框。每个对话框只调一次，用户之后拖成什么样都不再动；最大化的不动，除非它没有最大化/还原按钮（新式对话框都没有）：那样用户既拖不动边、也没有按钮还原，就先 `ShowWindowAsync(SW_SHOWNOACTIVATE)` 还原，等它真的还原了（下一次位置变化）再按上面的办法调，见 pitfalls.md“对话框一弹出来就是最大化的”；没有可拖边框的（有些 XP 风格的）只挪不改大小，它们不会重新排版。Windows 按程序记住对话框的大小（`HKCU\…\Explorer\ComDlg32\CIDSizeMRU`），同一个程序下次弹出来已经合适，不用再调。用 `SWP_ASYNCWINDOWPOS`，不等对话框的线程（它可能正忙或卡住）；搜索框等对话框到了新位置再出来，免得先在旧位置旁边闪一下（最多等 300 毫秒）。要的空间比判断“放得下”时多 1 逻辑像素，见 pitfalls.md“差一个像素”。
  - **一眼认出是 Win顺 的**：和对话框都是深色（或都是浅色）时，搜索框容易看成对话框自己的一部分。所以 Win顺 的图标从它后面探出头来（`win::PeekingLogo`）：图标 32 逻辑像素见方，露出四分之三，另外四分之一在搜索框后面。从哪条边探出来，按上、左、右、下的顺序取第一个不出工作区、也不压着对话框的；都压着对话框就取第一个不出工作区的，都出去就不显示。所以搜索框在对话框下方时图标在它左端外面（从顶边探出会压住对话框的下边），对话框贴着屏幕左边时在右端外面，搜索框在对话框左右两边时在它顶上。从上下边探出时离左端 20，从左右探出时和输入框那一行居中（列表打开时窗口变高，图标不跟着跳）。从顶边探出时图标正立，藏起来的是它下面四分之一；从别的边探出时转成叶子（右上那一格）正对外面：向左逆时针转 135°，向下顺时针转 135°，向右顺时针转 45°，成了菱形，和叶子相对的那个角藏在窗口后面（菱形对角线的四分之一）。斜着的边落不到像素网格上，所以斜放时用 ico 里最大的 256 像素那张转好，再平滑缩小（每个像素取它盖住的那些的平均），边缘是抗锯齿的；正立时仍用对应尺寸那张，不经缩放。菱形的外接方框是边长的 √2 倍，48 像素的图标占 68 像素见方。搜索框的窗口没法有透明的部分，所以图标是另一个分层窗口（`UpdateLayeredWindow`，逐像素透明），只画露出来的那一部分，边正好贴着搜索框的边，看起来就是被挡住了一截。它不接鼠标（`WS_EX_TRANSPARENT`），点上去点到的是下面的窗口；不激活、置顶。图标取自 exe 里的 app.ico，32 逻辑像素在 100%、125%、150%、200% 下正好是 ico 里有的 32、40、48、64，每个尺寸都是对着像素网格画的，不经缩放。搜索框显示完第一帧、不再隐身时它才出来，跟着搜索框移动、隐藏。启动器（双击 Ctrl 的搜索窗口）也有同一个图标（`WindowLogo`），一般在它顶上；`revealLauncher` 时出来，预先画的那一帧不出来，隐藏时跟着隐藏。它和窗口没法真是一个窗口：窗口的云母背景、圆角、边框和阴影由 DWM 按整个窗口画，留一块透明的地方放图标，那块也会有边框和阴影。所以图标在窗口自己的 `WM_WINDOWPOSCHANGED` 里跟着挪（`SetWindowSubclass`，和 `Placement` 一样），拖动、滑回原位时和窗口在同一刻动，看起来是一体的；不等 Qt 的 `xChanged`，那要晚一拍（见 pitfalls.md）。
  - 搜索用同一个引擎的“文件”范围；收藏的文件夹排最前，打开对话框里当前文件类型（文件类型列表里写的 `*.txt` 之类）的文件排在别的文件前面，另存为对话框里文件夹在前。`Ctrl+Enter`（只在打开对话框里）转过去后直接按“打开”。什么都没输入时依次列：文件管理器里开着的文件夹（最多 5 个，每个窗口正在显示的标签在前，右边标着是资源管理器、Total Commander 还是 Directory Opus 的）、剪贴板里的路径（在资源管理器里复制的文件或文件夹，即 `CF_HDROP` 的第一个；或复制成文字的路径，`PathText` 认引号、`file:///`、`%变量%`）、收藏（`favorites.json`，和启动器共用一份；右键或“更多”菜单加入；本机盘上已经不在的不列，网络上的不查）、最近用过的文件夹（Windows“最近使用”里的快捷方式和 Win顺 打开过的东西轮流取，关掉“记住打开过的项目”就都不列）。这些在后台线程上查，查完没有变化就不刷新列表，免得选中的行跳回第一行。查文件在不在只查本机的盘：网络驱动器（`GetDriveType` 是 `DRIVE_REMOTE`）和共享上的不查，服务器断了的话一查就要等很久，后面的请求都得排队。列表里哪一行就是对话框当前所在的文件夹，标“当前位置”。
  - **输入路径**：框里是一个路径（`C:\`、`D:\Pro`、`\\nas\share\`，也认引号、`file:///`、`%变量%`；`pathtext::splitTyped` 在最后一个 `\` 处分开）时不搜索，直接列那个文件夹里的东西：输入到 `\` 为止就列全部，第一行是这个文件夹本身（回车就转过去）；后面还有半个名字，就按搜索框同样的规则匹配（名字里任意位置，也认拼音），文件夹在前，再按匹配程度和资源管理器的顺序（数字按大小）。隐藏的不列。`Tab` 把选中的文件夹填进框里接着往下列，`Shift+Tab` 回到上一级，像命令行补全路径。不用索引，因为索引排除了一些文件夹、也不收网络共享，直接列出来的才是磁盘上现在有的。列文件夹在搜索框自己的另一条后台线程上（`ComWorker` 第二个），慢的网络共享不会卡住别的查询；打字时只有最后一次的结果算数。
  - 选中后先把前台交还对话框，等它恢复了键盘焦点再操作；选的是文件，就转到它的文件夹，再把文件名填进文件名框。每一行的右键菜单：转到、直接打开（文件，打开对话框）、在列表中展开（文件夹，同 `Tab`）、复制路径（`Ctrl+Shift+C`）、加入收藏夹或从收藏夹移除、收藏所在的文件夹（文件）。“更多”菜单还能“这次不显示”和“在某程序中不再显示”（按程序文件名记在设置里，`Ctrl+G` 在这些程序里照常可用）。输入框、按钮和每一行都有无障碍名称（`Accessible`），读屏软件能读出来。
  - **自动转过去**（默认关）：对话框第一次出现时转到文件管理器最前面的文件夹；之后从文件管理器切回对话框时，只有它显示的文件夹和离开对话框那一刻不同才转，只是过去看一眼就不动。“离开”和“切回”不要求前台直接在两者之间换：点任务栏按钮、`Alt+Tab` 时，任务栏、切换窗口、开始菜单会在中间到前台一下（第一版因此把对话框当成关掉了，切回来不转，issue #7）。所以记的是“最后在前台的对话框”（`m_lastDialog`，窗口还在就一直记着），文件管理器在它之后第一次到前台时记下那时显示的文件夹，并把这个对话框记进“去过文件管理器”（`m_wentToManager`）；对话框再到前台时从里面取走它，才算“从文件管理器回来”。中间到过 Win顺 的搜索框或剪贴板（同伴）就取消。Listary 6 一律自动转，用户嫌它把程序自己记住的位置冲掉了（论坛帖“Disable Auto Quick Switch in Listary v6”）。第一次转之前先等对话框自己的位置显示出来（刚出现时地址栏是空的），记下来，搜索框右边就换成“回到原来的文件夹”。
  - **WPS Office 自己的对话框**（金山的 `KcfdFileDialog`）：是 Qt 画的窗口（`Qt5QWindowIcon`，`WS_POPUP`，属主是文档窗口），里面没有子窗口，地址栏、文件名框只有 UI Automation 看得到（WPS 以管理员身份运行，Win顺 也是，所以看得到）。前台换成 WPS 的程序（`wps.exe`、`et.exe`、`wpp.exe`、`wpspdf.exe`、`wpsoffice.exe`）里一个有属主的 Qt 窗口时，在 `DialogJump` 的后台线程上用 UIA 看它根元素的类名，按左边那个按钮的名字（“打开”还是“保存”）分打开和另存为，结果按窗口记下（`filedialog::probe`）；界面线程上的 `filedialog::kind` 只查这个记录，WPS 卡住也拖不住 Win顺。只问 WPS 的窗口：Qt 程序第一次被 UIA 问到才打开自己的无障碍支持，之后一直开着。
    - 换文件夹：先确认是文件夹（不存在的路径 WPS 会弹自己的提示框），点面包屑后面的空白（`KcfdLocSpaceButton` 的 Invoke）出来输入框 `KcfdLocNavigationLineEdit`，把焦点放进去，用 `ValuePattern` 填路径，往对话框窗口投递回车。Qt 把回车交给有焦点的控件，所以填之前、投递之前都用 `GetFocusedElement` 确认焦点还在这个输入框里，否则回车会落到文件名框里，等于按“保存”。输入框收起来就算到了；焦点这时停在面包屑后面，挪回文件名框。填文件名用文件名框（`KcfdFilterWidget` 里的 `kd::KDTextField`）的 `ValuePattern`，“打开”用按钮的 `InvokePattern`。
    - 不读它在哪个文件夹（面包屑的名字 UIA 给得不全、不及时），也不读文件类型（UIA 报的是一开始的类型），所以 WPS 对话框里没有“当前位置”标记、收藏当前文件夹和“回到…”。
    - 实测（2026-10-10，WPS 文字的另存为对话框）：`Ctrl+G` 158–195 毫秒，从搜索框选文件夹 178–187 毫秒、选文件 193 毫秒（含填文件名）；地址栏换文件夹本身 9–34 毫秒。对话框原来在 278 像素高处，下面放不下搜索框，没有可拖的边框，被往上挪到 79。WPS 的“打开”对话框还没实测。
  - **后台线程**：问资源管理器、操作对话框都在 `ComWorker` 上做（自己拥有的 `std::jthread`，COM 单线程套间），一次一个、按先后顺序，后来的请求排队，不丢；退出时等当前这个做完。`DialogJump` 一个，`DialogBar` 两个（看周围的建议、列输入的文件夹）。
  - 实测（2026-10-08）：打开、另存为、选择文件夹、高 DPI 程序、XP 风格五种对话框，按下 `Ctrl+G` 到对话框换好 46–162 毫秒；从搜索框选文件夹 92–99 毫秒，选文件 181–200 毫秒（含填文件名），`Ctrl+Enter` 打开 107–134 毫秒；走文件名框 82–89 毫秒。自动转过去：对话框窗口出现后约 360 毫秒到位（含等它显示自己的位置），从资源管理器切回来 53–62 毫秒。2026-10-09：输入文件夹路径回车 159–217 毫秒，`Tab` 进去再选文件 104–107 毫秒，`Shift+Tab` 回上一级再回车 81–82 毫秒，输入整条文件路径回车 96–113 毫秒，选资源管理器里复制的文件 102–105 毫秒；资源管理器在盘符根目录（`F:\`）时 `Ctrl+G` 64–132 毫秒。给搜索框腾地方：对话框显示后 0–78 毫秒调到位（有时它一出现就已经是调好的大小），搜索框随后 31–62 毫秒出现在最终位置。
  - **Total Commander 和 Directory Opus 也认**（`filemanager::`）。`Ctrl+G`、自动转过去和搜索框的建议，都按窗口前后顺序（`EnumWindows`）在三种文件管理器的窗口里找：每个窗口正在显示的文件夹在前，后面才是藏在后面的标签、另一栏。只认盘上的文件夹，压缩包里、FTP、插件的虚拟文件夹不算（对不上 `GetFileAttributes` 的目录就扔掉）。
    - **Total Commander** 给主窗口（`TTOTAL_CMD`）发 `WM_USER+50`：参数 1000 回答左栏（1）还是右栏（2）有焦点，9 和 10 回答左右两栏上方路径那一行的窗口，读它的文字，形如 `c:\Windows\*.*`，去掉最后的过滤条件、盘符改大写（`pathtext::folderFromTotalCommander`）。窗口再窄、路径再长，这段文字也是完整的（显示时才截短）。只看两栏正在显示的，不看标签。
    - **Directory Opus** 用它自带的 `dopusrt.exe /info <文件>,paths`：把每个窗口（lister）的每个标签写成 XML，`tab_state="1"` 是有焦点那一侧正在显示的标签，`2` 是另一侧的，`lister` 是窗口句柄，元素里的文字是真实路径（`display_path` 是本地化的，“C:\用户”）。每次约 50 毫秒，`dopusrt` 退出时文件已经写好。它没有窗口开着时不问：问一次就会把它启动起来。`dopusrt` 必须用普通权限启动（`shell::startUnelevated`，拿桌面外壳的令牌），见 pitfalls.md。
    - **打开文件夹、打开所在位置**按设置“用哪个文件管理器打开文件夹”（`FileManager`）：`shell::open` 打开文件夹、`shell::reveal` 显示文件时交给选中的那个，启动失败或没装就照旧用资源管理器（`SHOpenFolderAndSelectItems`）。Total Commander：`/O /T /S /L="路径"`，在已经开着的那个里（`/O`）、有焦点那一栏（`/S`）开新标签（`/T`）；路径是文件时光标停在它上面，是文件夹时加 `/P`，开它的上一级、光标停在它上面。Directory Opus：`dopusrt /acmd Go "路径" OPENCONTAINER NEWTAB=findexisting,tofront`，文件和文件夹都是开上一级并选中它，已经有标签显示那个文件夹就用那个标签；它没在运行时 `dopusrt` 会把它启动起来。都用普通权限启动，不会多出一个管理员身份的文件管理器。设置里只列装了的（Total Commander 看注册表 `Software\Ghisler\Total Commander\InstallDir` 或正在运行的那个，可以是绿色版；Directory Opus 看 `App Paths\dopus.exe`），窗口回到前台时再看一遍。固定任务栏按钮那一步仍用资源管理器（`shell::revealInExplorer`）：要它的右键菜单。
    - 实测（2026-10-09，Total Commander 11.58、Directory Opus 13.25）：同一个打开对话框，依次在 Total Commander、Directory Opus、资源管理器之后按 `Ctrl+G`，每次都转到刚才那个窗口显示的文件夹；搜索框的建议里各自标出来源。设成 Total Commander 或 Directory Opus 时，在启动器里回车打开文件夹、`Ctrl+Enter` 打开所在位置都在它里面开，并且它到了前台，光标（选中）停在那个文件上。
- **双击 Ctrl 用 Raw Input，不用键盘钩子。** 低级键盘钩子会被系统里每一次按键同步调用，钩子一慢就拖慢所有程序的打字；回应超时后 Windows 还会悄悄把它摘掉，双击 Ctrl 从此失灵。Raw Input 是按键之后才异步送来的消息（在单独的线程上接收），两个问题都没有。
- **只在录快捷键时临时装低级键盘钩子。** 设置里点了快捷键方框，到录完、按 Esc 或焦点离开为止，`ShortcutCapture` 在自己的线程上装 `WH_KEYBOARD_LL` 钩子（PowerToys 的快捷键框也这样做）。设置窗口在前台时，按键在 Windows、Qt 和其他程序处理之前就被拿走，换成普通的按键事件交给录制框。不这样的话，Alt+Space 被 Qt 拿去弹系统菜单，Alt+F4 关掉设置窗口，Win+E 打开资源管理器，别的程序注册了的组合键（PowerToys Run、Copilot 常用 Alt+Space）直接打开那个程序，都录不上。现在都能录下来，注册不上的照常提示“已被其他程序或系统占用”。只吞录制开始后按下的键，以及这些键的抬起：之前就按着的键 Windows 要看到它完整抬起，否则会以为它一直按着。Win 键按下和抬起都不让 Windows 看到，所以不会弹开始菜单。音量、媒体键照常放行。钩子装不上时，录制框退回 Qt 自己的按键事件（录不到 Alt+Space）。
- **剪贴板历史有自己的窗口。** `Win+V` 打开的是 `ClipboardWindow.qml`（里面是 `ClipboardPage.qml`），不是启动器的另一页：它要出现在粘贴去的地方旁边（在哪个搜索框里按，就在哪个框下面打开；在别的程序里按，就在输入光标下面），大小也和启动器不同；两件事挤在一个窗口里时，启动器的每处布局、每个开关逻辑都得先问一句“现在是不是剪贴板”。云母效果、主题、多选和右键菜单仍是同一套，窗口启动后 1.5 秒预先画一帧（同启动器，见 `prewarmClipboard`），打开时先遮住、画好第一帧再显示。历史在内存里（每条文字的前 64K 个字符），打开不用等任何东西。
  - **点一条就粘贴，预览按需打开。** 列表里点一下（不按 Ctrl、Shift）就粘贴这一条，和 Windows 自带的剪贴板面板一样；点的是多选里的一条，就把选中的几条一起粘贴。平时窗口只有列表（480 宽）；每行右边的眼睛按钮或 `Alt+P` 在右边打开当前这一条的预览，窗口往右变宽，方向键换行时预览跟着走，`Esc` 先收起预览。预览宽 280～400，取列表右边到屏幕边缘还剩的地方，这样窗口不用挪、列表和按钮停在鼠标下面不动；剩下的不到 280 时窗口才往左挪（实测：启动器靠右时窗口一挪，第二次点眼睛按钮就点在了旁边的固定按钮上）。
  - **接管 Win+V 不用键盘钩子。** `Win+V` 是资源管理器用 `RegisterHotKey` 占着的，别的程序注册不上（错误 1409）。资源管理器启动时读 `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\Advanced\DisabledHotkeys`，里面写着的字母它就不注册；所以打开设置里的开关时往里加一个 `V`（保留原有的字母），资源管理器重启后 Win顺 就能 `RegisterHotKey(Win+V)`。重启资源管理器是结束任务栏所在的那个 `explorer.exe` 进程（退出码非零）。Winlogon 只重新启动它在登录时启动的那个外壳，被别的程序重启过的它不管，所以结束前先复制这个进程的令牌：3 秒内没有新外壳，就用这个令牌 `CreateProcessWithTokenW` 启动 `explorer.exe`，权限和原来一样（Win顺 直接启动的话会带着管理员权限，任务栏上打开的一切也就都是管理员的）；这也不行（要用到“Secondary Logon”服务），就以用户自己的 `sihost.exe` 为父进程启动，子进程拿父进程的令牌。这几秒的等待放在后台线程，任务栏没回来时托盘通知告诉用户怎么手动启动。`TaskbarCreated` 广播说明新的资源管理器起来了，这时重新登记一次。关掉开关、恢复默认设置或卸载时把 `V` 去掉；开关从没打开过时，注册表里原有的 `V`（用户为别的程序加的）不动。代价：Win顺 退出期间 `Win+V` 没有反应。
  - **读剪贴板在单独的线程上。** `ClipboardWatcher` 有自己的线程和隐藏窗口，用 `AddClipboardFormatListener` 收通知，等 40 ms 让程序把各种格式放齐再读。读别人复制的内容可能要那个程序现场生成（Excel 画单元格的图、Word 转 RTF），所以只在没有文字时才读图片，图片转 PNG 也在这个线程上，界面不受影响。
  - **存进历史也不让主线程等磁盘。** `ClipStore` 的内存列表照旧只在主线程用，数据库连接和图片文件交给它自己的写库线程（`ClipStore::Writer`，按先后顺序执行的任务队列）。复制、粘贴后置顶、移进分组、改名、过期清理和清空都是先改内存，列表马上刷新，写库排进队列；新条目的 id 在内存里分配，接着库里记下的最大值往下排，删掉的 id 也不再用，所以不用等插入。要读磁盘的操作排在同一个队列里等结果，总能读到刚排进去的内容：粘贴时读全文和格式，删除时为撤销读出整条，撤销，新建和删除分组，读设置值。文字的哈希在监听线程上算好。图片写好之前 `imagePending` 为真，列表和预览先不给图片地址，写好后 `Listener::pictureSaved` 刷新那一行；粘贴和打开图片会先等它写完。写库失败（比如磁盘满）时，`Listener::lost` 把那条从列表里拿掉。退出时先把队列写完。实测和代价见 pitfalls.md 的“复制一大片带格式的内容，Win顺 卡一下”。
  - **删掉的历史当场还给磁盘。** 数据库开着 `auto_vacuum=FULL`：删除、过期清理、清空后，空出来的页在提交时就截掉，文件不会只涨不缩（作者电脑上删过大图后的 29.5 MB 降到 0.35 MB）。旧版建的库打开时转一次（`VACUUM`，在写库线程上）。不用 `INCREMENTAL`：Qt 对没有结果列的语句，`next()` 直接返回假，`PRAGMA incremental_vacuum` 每次只释放一页（见 pitfalls）。WAL 文件用后截到 1 MB 以内（`journal_size_limit`）。
  - **不记录的内容按 Windows 的规定来。** 带 `ExcludeClipboardContentFromMonitorProcessing`、`Clipboard Viewer Ignore` 格式，或 `CanIncludeInClipboardHistory` 为 0 的不记（密码管理器和 Windows 凭据管理器复制密码时会带上，Windows 自带的剪贴板历史也认这几个）；前两个不打开剪贴板就能判断，不会妨碍那个程序。另有一份按程序文件名排除的名单。
  - **粘贴回原来的窗口。** 窗口从隐藏状态打开时记下当时的前台窗口。粘贴时先等 Shift、Ctrl、Alt、Win 都松开（按着 Shift+Enter 时直接发 Ctrl+V，对方收到的是 Ctrl+Shift+V），再由剪贴板线程写入这一条原来的各种格式（文字、HTML、RTF、文件列表、PNG + DIB），然后把前台交还给那个窗口（Win顺 这时在前台，所以 `SetForegroundWindow` 可以成功；在别的程序上打开时它一直在前台，见下面的“不抢焦点”），等它真的到了前台、再等 60 ms（它要先把焦点放回输入框，否则按键落在窗口上就丢了）再用 `SendInput` 发 `Ctrl+V`；Git Bash（mintty）和 PuTTY 发 `Shift+Insert`。Win顺 以管理员身份运行，所以管理员权限的程序里也能粘贴。剪切来的文件以后再粘贴一律按复制处理，不会再移动一次。
  - **粘贴到 Win顺 自己的输入框。** 按 `Win+V` 时键盘在 Win顺 自己的输入框里（启动器的搜索框、对话框旁的搜索框、设置窗口里的输入框），剪贴板就粘贴回这个框：`App::focusedField` 取前台窗口里有焦点、接受输入的项（`Qt::ImEnabled`，只读的不算），在剪贴板窗口拿走焦点之前用输入法查询记下光标和选区。粘贴时照常写剪贴板（之后剪贴板里就是这一条），文字则不经剪贴板直接给那个框：框所在的窗口重新到前台，剪贴板窗口随之隐藏；对话框旁的搜索框万一已经藏起来了（对话框关了又开），先把前台交给对话框，它一显示出来就激活它。等这个框真的有了焦点，先用一个只带 `Selection` 属性的 `QInputMethodEvent` 恢复光标和选区，再用一个带 `commitString` 的把文字打进去，和输入法上屏一样：替换选中的部分、`Ctrl+Z` 一步撤销，`TextInput`、`TextEdit` 都认（`TextField.cpp`）。单行的框里多行文字合成一行（见下一条），文件列表填路径，图片不粘贴。`Esc` 和再按一次 `Win+V` 走同一条路，只是不打字。
  - **从 Win顺 的输入框打开，就挂在它下面。** 剪贴板窗口左边和这个框（输入项的父项：启动器的搜索栏、对话框旁搜索框的那一行、设置里的输入框）对齐，在它下面 4 px（`Placement::attach`）；下面放不下最少的行数而上面更宽裕时，开在框的上面，窗口底边贴着框，行数按那边的高度算（对话框旁的搜索框在屏幕底部时就是这样，剪贴板盖在对话框上）。启动器的列表、空状态和底栏这时收起来，只剩搜索框（`Main.qml` 的 `clipboardBelow`）；框设了 `persistentSelection`，选中的部分照样显示，粘贴会盖掉哪些字一眼看得到。对话框旁的搜索框失去焦点时列表本来就收起；剪贴板窗口在前台时它照常显示，因为 `DialogJump` 把剪贴板窗口和它一样当作对话框的同伴（`setCompanions`），前台换成它们不算离开对话框。这种挂着的位置不记住；用户拖动后就停在放下的地方，下次照旧挂在框下面。露出的图标只在从别的程序打开时显示：挂在框下面时，那个框的窗口已经有一个。
  - **从别的程序打开，就挂在输入光标下面。** 和 Windows 自带的剪贴板一样：按 `Win+V` 时眼睛在正在打字的地方，粘贴也落在那里，鼠标可能停在屏幕另一头。光标那一行当作一个框，规则同上（`Placement::attachNative`，物理像素按所在屏幕换成 Qt 的逻辑像素，向外取整，框把整个光标包住）。找光标（`win::TextCaret`）依次问三处，第一个知道的算数：系统光标（`GetGUIThreadInfo` 的 `rcCaret`，经典程序都有，Firefox 和控制台也为放大镜设了一个；不发消息，立刻读到）；无障碍的光标对象（`WM_GETOBJECT` + `OBJID_CARET`，Chrome、Edge、VS Code 这些自己画光标的 Chromium 程序给的就是它）；UI Automation 的 `TextPattern2::GetCaretRange`，没有就取选区的末端（Windows Terminal、XAML 程序）。后两个要问对方程序，它可能慢或者卡死，所以放在自己的线程上（MTA），最多等 100 毫秒（`kCaretWait`），超时就按找不到处理，上一次还没问完时直接不问。UI Automation 的连接和单次调用超时设成 300 毫秒，不用默认的 2 秒和 20 秒。对 Chrome 系和 Firefox 不用 UI Automation：它们一被问就打开整套无障碍支持，之后一直变慢。必须在剪贴板窗口拿走焦点之前问：程序失去焦点就把光标藏掉或销毁。不感知 DPI 的程序报的是缩放前的坐标，按窗口的 DPI 和显示器的 DPI 之比换算。高于屏幕四分之一、或者不在那个窗口上的“光标”不算。找不到时剪贴板的左上角在鼠标指针尖下面 4 px，像右键菜单，指针压着的是标题栏而不是某一条，免得手一抖就粘贴了。露出的图标不压光标那一行（`WindowLogo::setAvoid`），剪贴板在这一行下面时图标就从左边探出来。拖动后停在放下的地方，不记住。实测（2026-10-09，150%）：WinForms 文本框（不感知 DPI 和感知的两种）、Firefox、控制台都由系统光标找到；Edge 由光标对象找到，问了 7 毫秒；Windows Terminal 由 UI Automation 找到，3 毫秒；按钮上没有光标，问了 10–14 毫秒后开在鼠标处。从按下快捷键到剪贴板到前台 14–45 毫秒。
  - **在别的程序上打开时不抢焦点**（`KeyRouter`）。和 Windows 自带的剪贴板一样：那个程序留在前台，它的输入框留着键盘焦点，凡是一失去焦点就关掉的东西（VS Code 的命令面板、浏览器地址栏的建议列表、自动补全、输入法正在组的字）都还开着，粘贴就落在光标原来的地方。剪贴板窗口不激活地显示（`_q_showWithoutActivating`），`WindowFrame::setNoActivate` 给它 `WS_EX_NOACTIVATE`，`WM_MOUSEACTIVATE`/`WM_POINTERACTIVATE` 回 `MA_NOACTIVATE`，点它也不激活；拖标题栏直接走 `SC_MOVE`（系统的 `WM_NCLBUTTONDOWN` 处理会先激活窗口）；`WM_NCACTIVATE` 按激活处理，云母照常显示。键盘靠一个只在窗口开着时存在的低级键盘钩子，在自己的线程上（每个按键都要等钩子回答，所以不放在主线程，判断只看按键本身）：只拿剪贴板用得上的键（打字、方向键、`Enter`、`Esc`、`Tab`、`Delete`、`Alt+1`～`9`、`Alt+P`、`Alt+F4`、输入框的 `Ctrl` 组合键），换成 `QKeyEvent` 交给窗口里有焦点的那一项（`QQuickItem::scopedFocusItem` 一路找下去，不处理就往父项传，和窗口自己有焦点时一样）；`Win` 组合键、`Alt+Tab`、媒体键、F 键、别的 `Ctrl` 组合键照常给前台程序和别人的全局热键。字按前台程序的键盘布局用 `ToUnicodeEx` 算出来（标志位 4，不动系统的死键状态），所以搜索里打的是拼音字母，不经过输入法——搜索本来就支持拼音。`Shift`、`Ctrl`、`Alt` 本身照常给前台程序（`Alt+Tab`、`Ctrl`+点击都要它们），但它不能以为它们是单独按的：单按 `Alt` 会打开菜单栏（VS Code 的菜单栏一拿焦点命令面板就关），单按 `Shift` 会切换中文输入法的中英文。所以按着它们时拿走一个键，就补一个谁都不认的键（`vkE8`，AutoHotkey 屏蔽开始菜单也用它），单独松开的 `Shift`、`Alt` 也先补一个再放过去；`Ctrl` 不补，双击 `Ctrl` 照常打开启动器。点击不拿：鼠标钩子只看按下的位置，不在 Win顺 的窗口上就收起剪贴板；`EVENT_SYSTEM_FOREGROUND` 报别的窗口到了前台也收起。收起后钩子不马上卸：拿走的键还按着时，它们的松开也归它（否则粘贴的 `Enter`、关闭的 `Esc` 松开时会单独落到程序里），最多再留 2 秒。粘贴时程序本来就在前台，等修饰键松开、写好剪贴板，收起窗口就发 `Ctrl+V`，不用等它回到前台。Win顺 自己发的按键（`Ctrl+V`、补的键）带 `kOwnInput` 标记，钩子放过。要拿焦点的时候才激活：给分组起名（要用输入法打中文）、打开链接或文件（新开的程序只有从前台程序那里才能到前台）。开始菜单、搜索这类外壳弹出层开着时照旧激活（它们总在所有窗口上面，`bringToFront` 先关掉它们）。钩子装不上时也照旧激活。实测（2026-10-09，150%，WinForms 测试窗口记录自己的激活、焦点、菜单和按键）：打开、打字、方向键、`Enter` 粘贴、点一条粘贴、`Esc`、点别处、拖动、再按快捷键、`Alt+P`、`Ctrl`+点击多选，测试窗口全程在前台、输入框一直有焦点、没有一次失活或菜单激活；在测试窗口里单按 `Shift` 会切换输入法（对照），剪贴板开着时 `Shift+Tab` 和单按 `Shift` 都不切换；剪贴板开着时连按两次 `Ctrl+A` 不会被当成双击 `Ctrl`。单独开一个 VS Code（临时配置），`Ctrl+P` 后按快捷键，命令面板留着，`Enter` 后测试文字出现在命令面板的输入框里。
  - **哪个窗口失去焦点就隐藏哪个，但不是马上。** 剪贴板挂在启动器下面时，启动器没了焦点也不隐藏（焦点就在剪贴板窗口上）；剪贴板窗口没了焦点时排队检查一次再隐藏，而不是在 `activeChanged` 里当场隐藏：焦点从它转到 Win顺 的另一个窗口（粘贴回去的那个框）时，Qt 可能先报一次“没有窗口有焦点”。隐藏时如果焦点也不在启动器上（点到了别的程序、粘贴到了别处），挂着它的启动器一起隐藏；点一下启动器的搜索框，剪贴板隐藏、启动器留下，接着搜索。
  - **钉住**（issue #8，`Clipboard::pinned`，右上角的图钉）。钉住后窗口一直在最上面（它本来就是 `WindowStaysOnTopHint`），凡是会把它收起的事（点别处、别的程序到前台、粘贴完、打开启动器）都改成“把键盘还回去”（`App::hideClipboard` 开头转给 `releaseClipboard`）：停掉 `KeyRouter`，窗口 `WS_EX_NOACTIVATE`。这时键盘一直是前台程序的，点一条就粘贴到点的那一刻在前台的程序（`Clipboard::paste` 里换 `m_target`），它不失去焦点，所以可以一条接一条地填。要用键盘挑：再按一次快捷键，或点搜索框（`keysWanted`），走和从别的程序打开时一样的 `KeyRouter`（`engageClipboard`，目标换成此刻在前台的程序）；粘贴完或 `Esc` 再还回去，`Esc` 时窗口自己有焦点的话把前台交还给那个程序（`keysReleased` → `releaseClipboard(true)`；粘贴后、打开文件后不交还，免得把刚打开的程序压下去）。起分组名、打开链接要焦点时照常激活（`activateClipboard` 钉住时也认）。取消钉住就像刚在前台程序上打开：键盘转过来，点别处收起。关窗口要先取消钉住（`Alt+F4` 例外，直接关）；每次从隐藏状态打开都是没钉住的。挂在 Win顺 自己的输入框下面时不显示图钉：那时它粘贴回那个框。钉住状态不存盘，位置也不记。
  - **多行文字粘贴进单行的框合成一行。** 和浏览器往单行输入框里粘贴一样（Firefox 的 `editor.singleLine.pasteNewlines` 默认也是换成空格）：每行去掉首尾空白，空行去掉，其余用空格连起来；只有一行的原样粘贴。Qt 的 `TextInput` 自己不做这件事，换行留在文字里。三个窗口（启动器、对话框旁的搜索框、设置窗口）都装了 `App::eventFilter`，在框收到按键之前截下 `Ctrl+V`、`Shift+Insert`（`QKeySequence::Paste`）：焦点在单行的框里（`textfield::isOneLine`）且剪贴板里有换行时，自己用 `QInputMethodEvent` 打进去，其余照常交给框。显示查询的地方（“没有找到“…””）另外把空白合成一个空格、过长时中间省略，不论查询从哪里来都不会铺开。
  - **自己写的不重复记录，也不读回来。** 写剪贴板的就是监听线程，写完记下剪贴板的序号，收到这次变化的通知时直接跳过，把那一条挪到最前；多条合并的不记录。不能写完再打开剪贴板读一遍：那正是目标程序处理 `Ctrl+V`、打开剪贴板的时候，抢不到的一方粘贴失败。写入时仍带一个私有格式 `WinShun.ClipboardEntry`（这一条的编号），别的程序把它原样放回剪贴板时也认得出来。启动时剪贴板上已有的内容（序号和启动时一样）记下来，但已在历史里的不算新复制，不挪位置、不改时间。
  - **SQLite 存储。** 每粘贴一次都要更新那一条的时间，SQLite（WAL，不每次同步到磁盘）只改这一行，程序崩溃也不会坏掉；Ditto 等工具也这样存。图片单独存成 PNG 文件，删除的条目在能撤销期间保留图片。只依赖 Qt 自带的 SQLite 驱动，部署时排除其他数据库驱动。
- **代替任务栏上的 Windows 搜索。** 点任务栏上 Win顺 的搜索框或按钮、按 `Win+S`，启动器在任务栏上方打开，和 Windows 自带的搜索一样（EverythingToolbar 也有这两种：“搜索框”和“固定图标”）。Windows 自带的搜索可以和它同时留在任务栏上，向导推荐隐藏。
  - **不接管 Windows 自带的搜索按钮或搜索框。** 2026-10-10 试过让它也打开 Win顺：低级鼠标钩子在资源管理器之前拦下点击。可点击到不了资源管理器，搜索框的按下、展开效果就都没了，像一个普通按钮，打开时图标也不变色（Windows 只在它自己的搜索打开时播放这些）。所以拿掉了，改成 Win顺 自己的入口（EverythingToolbar 也不接管 Windows 的，它在任务栏里放自己的按钮或搜索框）。
  - **Win顺 自己的搜索框**（设置里打开，默认关；`taskbar::SearchBox`，Windows 11）。一个 Win顺 的窗口做成任务栏（`Shell_TrayWnd`）的子窗口，和 EverythingToolbar 的搜索框一样。Win顺 是管理员权限，先用一个探测程序实测过（2026-10-10）：管理员权限的进程照样能把窗口挂进去（`CreateWindowEx` 直接以任务栏为父窗口），鼠标的悬停、离开、点击都收得到，压在任务栏的 XAML 内容（`DesktopWindowContentBridge`，同级的子窗口）上面，所以不需要另起一个不提权的进程。框用 Direct2D 画在分层窗口上（`UpdateLayeredWindow`，逐像素透明，圆角边缘是平滑的）。
    - **字打在启动器里，框只负责显示和点击。** 从框打开时，启动器自己的输入框还在、拿着键盘，只是看不见（`SearchBar.qml` 的 `inBox` 状态：宽 1 像素、透明），顶部只剩范围标签；输入框的文字、光标、选区和输入法正在拼的字，每变一次报给 App（`Launcher::fieldReported`），画到框里。这样按键、快捷键、输入法、打开文件时的前台权限，全是启动器原来那套，不用在任务栏里另做一个输入框（EverythingToolbar 是在任务栏里放了一个真的输入框，它不提权，和资源管理器同一个完整性级别）。输入法的候选窗口：App 回答输入框的 `InputMethodQuery` 时，把光标矩形换成框里光标所在的位置（`App::boxCaretInField`），框里的光标挪了就让 Qt 再问一次。
    - **点框时，原来的前台窗口照样失去激活。** 子窗口的 `WM_MOUSEACTIVATE` 返回 `MA_NOACTIVATE`，只能让任务栏自己不变成前台；实测原来的前台窗口还是失去激活，前台变成空的（见 pitfalls.md）。所以启动器开着时再点框，它先失去焦点：这时鼠标在框上，就再等 400 毫秒（`m_boxPressGrace`），框报来这次点击就把启动器拿回前台，光标放到点的位置（双击选中那个词，按住拖动选中一段）；没报来才隐藏。收到这次点击的是 Win顺 的线程，所以 Win顺 有权把自己的窗口带到前台。
    - **放在哪里**：默认在图标左边、挨着开始按钮（图标居中时；图标靠左时左边没地方，放在右边），离图标、托盘和小组件按钮各 8 逻辑像素；高是任务栏的 2/3，和 Windows 自带的搜索框一样（150% 时 48 像素）。开始按钮右边放不了：任务栏的图标一个挨一个，那里没有空地，放过去就盖住别的图标。
    - **空地多宽就多宽**（和 Windows 自带搜索的“搜索框 / 图标和标签 / 仅图标”一样）：空地有 140 逻辑像素就是完整的框（最宽 240），打的字显示在框里；不到 140 是图标加“搜索”两个字（宽度按字量出来，150% 下约 78），再窄就只剩图标、圆形、和框一样高。窄的两种不在框里打字：点它启动器照常在它上方打开，用启动器自己的输入框，框亮起来（悬停的底色）表示开着，再点一下收起，整块都可以按住拖动。打字途中框被挤窄了（任务栏上多了程序），启动器换回自己的输入框，字不丢；变宽回来不再换，免得打着字框跳。只有那一边连图标都放不下才换到另一边，两边都放不下才不显示。以前不到 140 就换边：图标居中、托盘旁边只有约 100 逻辑像素时，框根本拖不到右边（2026-10-10 用户反馈）。图标在哪用 UI 自动化量：任务栏里 AutomationId 为 `TaskbarFrame` 的元素的子元素，比任务栏窄 60% 以上的算图标，`SystemTrayIcon`、`WidgetsButton` 算障碍。子元素的位置和 AutomationId 用缓存请求一次取回（`FindAllBuildCache`，不留活的元素），3–5 毫秒；托盘图标在框架外的那种（有的版本）要搜整棵树，最多 250 毫秒搜一次。自动隐藏的任务栏没有完全露出来时不量。
    - **按住图标拖动换位置**：按住图标拖过系统的拖动阈值，或按住不动 350 毫秒，框就“浮起来”（放大 4%、底下一圈软阴影、光标变成移动），沿任务栏跟着鼠标走，可以暂时盖在图标上；拖的时候框就变成松手后在那一边的样子（宽度弹簧过去，抓的那一点留在鼠标下面），松手前就看得到会变成什么。松手后弹簧动画落到最近的空地上：框的中点在图标中线哪一边就放哪一边，以松手的地方为中心，那边连图标都放不下才去另一边。离图标那头或另一头（屏幕边、小组件、托盘）不到 16 逻辑像素就贴过去；记的是“哪一边、离哪头多远”（`SearchBox::Spot`，存在 `state.ini` 的 `[SearchBox]`：`Side=auto/before/after`、`From=icons/end`、`Offset` 逻辑像素），所以离图标近的跟着图标走，贴着屏幕边的就一直在边上。拖回默认位置时又存成 `auto`，跟着任务栏的对齐方式变。图标上只是点一下（没拖、没按住）照常打开启动器，在松手时打开。
    - **跟着图标走**：任务栏的线程上一有位置变化（进程外的 WinEvent，限定在它的线程上），马上量一次，之后每一帧都量（`DwmFlush` 定的节拍），直到 1.5 秒内再没有变化、并且图标停了 300 毫秒（最多 6 秒）。框每帧挪到量出来的位置，和图标一起滑。实测（2026-10-10，`tbmotion` 探测程序：两个最小化的窗口进出任务栏，逐帧截屏找开始按钮的位置）：任务栏的图标是一个接一个滑的，每个比前一个晚约 15 毫秒，一次滑约 280 毫秒，UI 自动化报的位置基本就是屏幕上的位置。但有一种读数走在屏幕前面：还没轮到滑的图标，先报终点，再跳回原处，然后才滑。来按钮时开始按钮有时就这样跳一次（一次读数），走按钮时开始按钮最后滑，约 370 毫秒里一直报终点（按钮越多越久）。所以小步（14 逻辑像素以内）直接跟；大跳先不动：会挡到图标的等 100 毫秒，留在空地上的等 800 毫秒，这期间读数回到框附近就作废，否则滑过去（挡到的 167 毫秒，其余按 Windows 的“点到点”曲线 333 毫秒）。以前是变化后 150 毫秒量一次、再隔 150 毫秒量一次，框跳两下；走按钮时先往右跳、再往左跳、再往右跳。现在连测四次，框和开始按钮的距离最多差 5–11 像素（滑得最快的那一帧，约一帧的路程），其余时候 1–3 像素。
    - **线程**：框的窗口在单独的线程上。别的进程的子窗口和那个进程共用输入队列，资源管理器卡住时，这个线程也会卡，但拖不住启动器。UI 自动化在第三个线程上（MTA，超时 2 秒）：它要问到任务栏上的每个窗口，框也在其中，框的线程不能在等它。第四个线程只管节拍：有动画或在跟着图标时，它每帧 `DwmFlush` 一次，给另两个线程各置一个事件；框的线程用 `MsgWaitForMultipleObjectsEx` 同时等消息和这个事件，等节拍时照样处理别的线程发来的消息。不用 `DCompositionWaitForCompositorClock`：它在显卡重置、远程桌面断开后可能永远卡在内核里，进程连结束都结束不了（Zed 编辑器踩过，zed-industries/zed#36934）。Win顺 退出或关掉这个设置时等这几个线程 2 秒，卡住了就丢下不等。
    - **资源管理器重启**：任务栏没了，框跟着销毁（`WM_DESTROY`），之后每秒找一次新的任务栏，最多一分钟；收到 `TaskbarCreated` 时也重新挂一次。
    - **样子**：圆角的长条，左边是 Win顺 的图标（从 exe 的 `IDI_ICON1` 按 16 逻辑像素取整数尺寸，ico 里正好有 16/20/24/28/32），右边是“搜索应用和文件”；打字时是启动器当前范围的提示。颜色跟任务栏的深浅色（`SystemUsesLightTheme`），不跟 Win顺 自己的主题；打字时边框换成我们窗口边线的灰（`Theme.windowEdge`：深色 #6A6A6A、浅色 #B4B4B4），粗细不变，都是 1 逻辑像素，和上面启动器的边一样（起初是 2 像素的强调色，用户嫌蓝、嫌粗）；高对比度时用系统颜色，打字时加粗成 2 像素。字体 Segoe UI Variable Text 半粗（600）14 逻辑像素，中文由 DirectWrite 回退到微软雅黑粗体。光标按系统的闪烁间隔闪。窗口比框四周各大 6 逻辑像素，留给浮起时的放大、阴影和光晕；那一圈全透明，鼠标穿过去点到任务栏。
    - **动画**（系统的“动画效果”关了就都没有）：时长和曲线照 Windows 11 自己的动效规范（learn.microsoft.com 的 “Motion in Windows”：进场 `cubic-bezier(0,0,0,1)`，已有的东西挪位置 `(0.55,0.55,0,1)`，温和的退场 `(1,0,1,1)`）。悬停 100 毫秒渐亮、200 毫秒渐暗；按下时框缩小 3.5%、图标缩小 14%，松开用弹簧弹回，带一点回弹（打字状态下点字只放光标，不缩）；变成打字状态时，底色和边框 250 毫秒过渡过去，边框外一圈 1 像素的灰色细环向外扩散并淡出（600 毫秒），图标轻跳一下；提示文字换了（打开、换范围）就旧的往左淡出、新的从右边淡入（200 毫秒）；出现时从 90% 放大、淡入（333 毫秒），没地方时淡出（167 毫秒）。画法：有动画时每帧在框的线程上重画（Direct2D 画一次不到 1 毫秒，框只有 360×48 像素）；框的位置可以停在两个像素之间，画的时候平移那个零头，文字用 `D2D1_DRAW_TEXT_OPTIONS_NO_SNAP`，慢慢挪时不会一格一格地跳；停下来时正好对齐像素，字和图标是清晰的。
    - 框在任务栏上时，`Win+S` 和开始菜单里打字也开到框上方，字进框里；固定的按钮还是开在按钮上方。
    - 实测（2026-10-10，25H2 26200，150%，深色任务栏）：点框后 Win顺 在前台；打的字、点在字后面的光标、双击选中的词都画对了，Esc 收起后框里回到占位文字；微软拼音打 nihao 时框里是带下划线的 ni'hao，候选条就在框上方，Esc 取消拼写后启动器还开着。
  - **按钮是另一个小程序。** Win顺 以管理员身份运行，固定到任务栏的程序要是需要提权，每点一下都弹 UAC。所以按钮是 `WinShunSearch.exe`（`src/stub`）：不提权，纯 Win32，不带 Qt，C 运行库静态链接。点一下它就启动，把前台权限交给 Win顺（`AllowSetForegroundWindow`，这次点击给了它这个权限），置位一个事件后退出；Win顺 用 `QWinEventNotifier` 等这个事件。事件由 Win顺 建，按默认会带“高”完整性标签，普通权限的进程写不了，所以建的时候给当前用户置位的权限、标签降到“中”（`taskbar::createEvent`）。事件只能让启动器显示或隐藏，不带任何参数，别的程序拿它也做不了别的。不用常驻进程：实测从启动它到 Win顺 收到事件，第一次 81 毫秒（Defender 扫描新文件），之后 8–14 毫秒（中位 9.6）。Win顺 没在运行时，它运行开机自启的计划任务（用户可以按需运行，不弹 UAC），没有计划任务就直接启动旁边的 WinShun.exe（会弹 UAC），等 Win顺 起来再置位事件。它的图标是放大镜（`resources/search.ico`），一看就是搜索，颜色和画法照 Win顺 的图标：同样粗细的不透明描边，四种颜色按位置在 OKLab 里渐变（左上红、右上绿、左下蓝、右下黄），镜片里是 16% 的淡色；手柄比镜框粗三分之一；24 像素起镜片里有一道小弧光，对应 logo 上叶子的叶脉。和 app.ico 一样由 `tools/make_icon.py` 按每个尺寸对着像素网格画，另外多了 30、36 像素：任务栏图标是 24 逻辑像素，125%、150% 下正好用上，不经缩放。
  - **固定到任务栏：Windows 问，用户点“是”**。`TaskbarManager.RequestPinCurrentAppAsync` 从 Windows 11 KB5074105（26100.7705 / 26200.7705）起对普通桌面程序开放，不用再申请受限功能的令牌（更早的版本要令牌，没有就退回下面的办法）。条件：请求的程序在前台、刚有用户点击、开始菜单里有它，而且对得上是它：程序自己设的 AppUserModelID 和开始菜单快捷方式上的一样（`LingCore.WinShun.Search`，`taskbar::kButtonAppId`）。没有这个 ID 时 `IsPinningAllowed` 一直是 false（2026-10-10 实测；微软的未打包示例也是这样做的）。快捷方式刚写上 ID，开始菜单约 3 秒后才认，所以先最多等 6 秒。请求的是 `WinShunSearch.exe --pin`：要固定的是它，Win顺 本身又是提权的。用户在设置里点“固定”，Win顺 经资源管理器以普通权限启动它（`SettingsEditor::pinTaskbarButton`，先确保快捷方式在、带着 ID），它弄一个透明的 1 像素窗口到前台，请求一发出就关掉这个窗口把前台还回去（问题是右下角的一条通知，可能很久没人回答；等待最多 2 分钟）。Windows 不问时（版本太旧、组策略禁止固定、上一次请求还没回答），它在资源管理器里选中那个快捷方式，让用户右键固定。安装程序建的快捷方式本来就带这个 ID（`AppUserModelID:`）。固定了没有，看 `%APPDATA%\Microsoft\Internet Explorer\Quick Launch\User Pinned\TaskBar` 里有没有指向它的快捷方式。
  - **设置向导**：设置 → 打开 Win顺 → 任务栏 →“代替任务栏上的 Windows 搜索”是一张四步的卡片：在任务栏上放 Win顺 的搜索框（一个开关；Windows 10 放不了搜索框，改为固定按钮），隐藏 Windows 的搜索按钮（推荐，两个也可以并存），用 Win+S 打开，开始菜单里打字。第一步做完是指框在任务栏上（Windows 10：按钮已固定）。第一个没做完的那步按钮突出显示，做完的一步打勾，标题下写着“已完成 n/4”。在 Win顺 外面做的也算：设置窗口监视任务栏固定的快捷方式所在的文件夹（`QFileSystemWatcher`）和 `SearchboxTaskbarMode` 所在的注册表键（`RegNotifyChangeKeyValue`，事件交给 `QWinEventNotifier`），一有变化就重新看一遍，窗口回到前台时也看。用 Win+S 打开或关上时直接重启资源管理器，不再让用户另点一个按钮。
  - **开在哪里**：点按钮时，鼠标下面是哪个任务栏（主任务栏 `Shell_TrayWnd`，或别的显示器上的 `Shell_SecondaryTrayWnd`）就开在哪个上方，沿任务栏以鼠标为中心，离任务栏和工作区边缘各 12 逻辑像素（Windows 11 的开始菜单和搜索也是 12）；任务栏在顶部、左右两边时开在它旁边。按 `Win+S` 时没有按钮的位置，开在鼠标所在显示器的任务栏上：图标居中（`TaskbarAl`；Windows 10 没有这个值，图标靠左）时在正中，否则在左端。那个显示器上没有任务栏，就开在平时的位置。挨着任务栏的那条边不动，窗口长高时往另一边长（`Placement::attachTaskbar`）。
  - **搜索框不跳**：从任务栏打开时，列表区一直是放得下的最多行数那么高（`Main.qml` 的 `fullHeight`），结果多了少了，搜索框都不会上下移动；什么都没输入、也没有最近记录时，列表区里写一句提示。
  - **打开和收起有动画**（`Placement::slideIn`、`slideOut`；系统关了动画就没有）：在任务栏上方打开时，启动器从任务栏后面滑出来，收起时滑回去，和 Windows 11 的开始菜单、搜索一样（微软的规范：任务栏上弹出的面板都向上滑出、向下收回）。做法同 EverythingToolbar：滑动期间把窗口放在任务栏下面一层（`SetWindowPos` 插到那个任务栏窗口后面，两者都还是置顶的）。插之前先把任务栏提到置顶窗口的最前面（`Placement::goBehindTaskbar`，和点一下任务栏时一样）：Windows 11 上前台的普通窗口常常在 z 序里排在任务栏上面，只是两者不重叠，只插到任务栏后面，启动器就也在那个窗口后面，整个看不见。任务栏挡住还没出来的部分，不用裁剪窗口（窗口区域会让 DWM 的圆角和阴影没了）。滑动途中它要是被激活（展开时又点了一下框，收起途中再点框把它叫回来），激活会把它提到最前面，盖住任务栏；所以滑动期间窗口过程（`Placement::Hook`）在 `WM_WINDOWPOSCHANGING` 里把任何往前提的请求改成“放到任务栏下面一层”（`m_under`），滑完才放开，并把它提回最前面。滑出 200 毫秒（`(0,0,0,1)`），内容晚一点跟上（从下面 24 逻辑像素处 260 毫秒滑到位，`Main.qml` 的 `Translate`）；收起 200 毫秒（`(0.3,0,1,1)`：一开始就动，越走越快），滑到任务栏后面才真正隐藏、清空查询（`App::finishHidingLauncher`）。起初用的是 Windows 规范里“温和的退场” `(1,0,1,1)`，可它头 70 毫秒只走 4%，看着像慢了半拍才开始收。别的显示器在下面时，只滑到不跨过去的地方，这时加上淡入淡出。在屏幕中间打开时（快捷键、双击 Ctrl）淡入（120 毫秒）并上升 16 像素（200 毫秒），收起时淡出（150 毫秒）并下沉 8 像素。整窗透明度用 `QWindow::setOpacity`（分层窗口的 `SetLayeredWindowAttributes`），实测 Mica、边线一起淡；只在窗口本来就是分层窗口（带 alpha，用了 Mica 的那种）时淡，否则直接出现。窗口逐帧用 `SetWindowPos` 移动（物理像素，相对它该在的位置），Qt 那边记的位置不变：滑动中位置变了（结果到了，窗口变高），就滑向新位置。收起途中又被叫出来（再点框、快捷键），从当时的位置滑回去；这时 Qt 可能晚一点才收到“点任务栏让它失去焦点”，所以打开后半秒内失去焦点、框模式下也先等 400 毫秒（`m_launcherShown`），不立刻关。但只在前台是空的（点框就是这样）、是开始菜单那一类，或者是任务栏且鼠标在框上时才等；前台换成了别的窗口（点了别的程序、桌面、任务栏的别处），就是用户要关，马上收起。以前不分这些，展开后半秒内点别处，要等 400 多毫秒才开始收。旁边的 logo 跟着一起滑、一起淡（`WindowLogo::follow`：每一步按 `Placement` 报的偏移、透明度和“在哪个任务栏下面”摆它），边沿按窗口停下的位置选，滑动中不换边；从任务栏后面滑出时它也在任务栏下面一层，滑出的距离加上 logo 露出的那截（`setOverTop`），一开始整个藏在任务栏后面。以前它在滑动时隐藏，停稳后才突然冒出来，收起时又先消失。时长是对着 Windows 自己的开始菜单定的（2026-10-10，150%，`openmeasure` 探测程序：在量的那一列后面垫一条白窗口，每几毫秒截一列像素找面板的上边沿，从按键或点击那一刻算）：开始菜单 65–80 毫秒出现、约 250 毫秒停稳，形状正是 `(0,0,0,1)` 跑约 200 毫秒；收起约 190 毫秒。Win顺 起初滑 333 毫秒，用户嫌慢；改成 200 毫秒后，从点框到出现 45 毫秒、停稳 220 毫秒左右，收起约 210 毫秒。显示前等新结果最多 60 毫秒（`m_revealTimeout`，以前 150）：等不到也先滑出来，结果稍后在滑动中换上。收起途中 60 毫秒再点框，从半路滑回原处。连续快速开关（2026-10-10，从点框算）：展开后 80～150 毫秒点别处，20 毫秒内开始往下收，213 毫秒隐藏（以前 420 毫秒才动、620 毫秒隐藏）；收起头 50 毫秒走 16%、100 毫秒走 39%（以前 2%、11%）。
  - **再点一下收起**：点任务栏时启动器先失去焦点、隐藏，按钮的程序要到松开鼠标才启动（0.1–0.3 秒后）。所以隐藏后 500 毫秒内来的点击不再打开它，否则点一下关掉、马上又弹出来（EverythingToolbar 也是 500 毫秒）。
  - **Windows 自带的搜索按钮藏不掉**：`HKCU\Software\Microsoft\Windows\CurrentVersion\Search` 的 `SearchboxTaskbarMode` 写 0 就隐藏，但 Windows 11（25H2 实测）的用户选择保护驱动（UCPD）不让任何别的程序写这个值，自己编译的程序、管理员权限都不行（错误 5）。设置里只读它（组策略 `SearchOnTaskbarMode` 优先），还在任务栏上就给一个按钮打开任务栏设置（`ms-settings:taskbar`），让用户自己选“隐藏”。
  - **`Win+S` 和截图键**：接管方法和 `Win+V` 一样（DisabledHotkeys 里加 `S`，重启资源管理器）。资源管理器按字母放手，`S` 让它连 `Win+Shift+S`（截图）一起不注册，所以 Win顺 拿到 `Win+S` 后也注册 `Win+Shift+S`，替用户打开截图。`Win+Ctrl+S` 不是资源管理器注册的，不受影响。`Win+Q` 也打开搜索，但不接管：`Q` 会带走 `Win+Ctrl+Q`（快速助手），`Win+Q` 本身又很少有人用。
    - 截图不能由 Win顺 直接启动：管理员进程启动的截图工具也带管理员权限（实测完整性级别为“高”）。所以交给 `WinShunSearch.exe --screenclip`，经资源管理器以普通权限启动。它照资源管理器的做法打开 `ms-screenclip:///?source=HotKey`（资源管理器启动截图工具的命令行就是这个），并且指定截图工具自己注册的类（`SEE_MASK_CLASSNAME`，`AppX…`，从它的包注册信息里读）：按用户的协议关联打开，在作者电脑上弹出了“你要如何打开”。实测出遮罩 376–424 毫秒，原生的 `Win+Shift+S` 是 292–375 毫秒。没有新版截图工具时退回 Windows 10 的 `SnippingTool.exe /clip`。
    - 只在 Win顺 确实拿着 `Win+S` 时代管截图键。关掉开关后、资源管理器重启之前（releasing）也去注册，会抢在新的资源管理器前面拿走 `Win+Shift+S`；它只在启动时注册一次，之后谁也没有。
    - 代价和 `Win+V` 一样：Win顺 退出期间这两个键没有反应。卸载时把 `S` 去掉（`GiveBackKey`），资源管理器下次启动时拿回去。
  - 实测（2026-10-09/10，25H2 26200，150%）：真的点任务栏上固定的按钮，64 毫秒后启动器在前台（含资源管理器处理这次点击、启动按钮程序），水平中心正对按钮、离任务栏 12 逻辑像素；再点一下收起，1.2 秒后仍是收起的（没有被这次点击重新打开）。直接运行按钮程序到启动器在前台 55 毫秒（含 PowerShell 启动它的时间），再运行一次 32 毫秒收起；`Win+S` 7 毫秒到前台，再按一次 16 毫秒收起；开关打开、关掉各重启一次资源管理器后，`Win+S`、`Win+Shift+S` 分别在 Win顺 和资源管理器手里。
  - **首页：常用应用**。从任务栏打开、还没打字时，列表区上方一排最多 6 个最常用的应用（`Main.qml` 的 `showHome`），下面是“最近”。`↑` 从第一行进到这一排，`←` `→` 选，`Enter` 打开，`↓` 回到列表。排序（`frequentApps`）：先是从 Win顺 打开过的应用，按次数乘以新近程度（一周内算满，一个月内七成，三个月内四成，再早两成）；不够 6 个时，用 Windows 记下的、60 天内启动过的应用补上（`windowsAppUses`，读 `HKCU\…\Explorer\UserAssist\{CEBFF5CD-…}\Count`，名字 ROT13，72 字节的记录里第 4 字节起是启动次数、第 8 字节起是获得焦点次数、第 60 字节起是最后启动时间）。Windows 11 上这里的启动次数大多是 0，时间是准的，所以分数取“启动次数 + 焦点次数的十分之一”，至少按 1 算。它记的名字和开始菜单“所有应用”里的应用 ID 是同一种写法（`{已知文件夹 ID}\相对路径`，商店应用是 AUMID），直接对；ID 是 AUMID 的桌面程序（Word 的是 `Microsoft.Office.WINWORD.EXE.15`）再按展开后的程序路径对。卸载程序、说明文档和 Win顺 自己不算。关掉“记住打开过的项目”时这一排也不显示。次数记在最近使用记录里（`History`：每行 `路径\t次数\t最后时间`，以前只有路径的一行按打开过一次、时间不详读）。
    - 每格 120 × 96 逻辑像素，图标在格里的 (44, 16)，这一排从 20 起：都是 4 的倍数，125%、150%、175%、200% 下都落在整像素上；竖直方向再按它在窗口里的位置补一个亚像素的平移（同结果行）。图标 32 逻辑像素，按原尺寸取、不平滑，150% 下正是 48 像素的那张。
  - **在开始菜单里打字也用 Win顺**（设置里打开，默认关；`StartMenuTyping`）。开始菜单在前台时打的第一个能打出字的键（字母、数字、标点、小键盘）被截下，启动器在任务栏上方打开；这个键和之后打的键都先存着，等启动器拿到键盘，再按原顺序用 `SendInput` 发进去（标成 Win顺 自己的输入），和直接在搜索框里打一样经过输入法。截下第一个键之后，回车、方向键、`Esc` 也存着按顺序发过去，“打完字马上回车”照样打开第一个结果。Win、Ctrl、Alt 组合照常给 Windows；开始菜单开着时按一下左 Alt，这一次就还用 Windows 自带的搜索（EverythingToolbar 也是左 Alt）。
    - 低级键盘钩子只在开始菜单（或 Windows 搜索）在前台时、以及存着键等启动器的这一会儿装着：一个进程外的 `EVENT_SYSTEM_FOREGROUND` 事件看前台是不是 `SearchHost.exe`（25H2 上开始菜单开着时前台就是它）、`StartMenuExperienceHost.exe`，或 Windows 10 的 `SearchApp.exe`、`SearchUI.exe`。钩子在自己的线程上，线程优先级调高、关掉省电降速（`ThreadPowerThrottling`），钩子回调只看按键本身就决定。存着的键 3 秒内没送出去（启动器没出来）就丢掉。
    - 关开始菜单不用另想办法：启动器显示时 `win::bringToFront` 本来就会先发一个 `Esc` 关掉它（见 pitfalls.md“开始菜单开着时双击 Ctrl”）。这个 `Esc` 带着 Win顺 自己的标记（`kOwnInput`，重新发的键也带），钩子放它过去，它照常到开始菜单。别的程序注入的键（AutoHotkey、PowerToys 映射出来的，屏幕键盘打的）照样算打字。
- **D3D11 渲染 + FreeType 字体引擎。** 界面字体阿里巴巴普惠体没有字体微调，GDI 下中文横笔画会糊成两行像素；FreeType 能把它们对齐到像素上。但软件渲染器会按估算的字形边界裁剪文字，FreeType 的字形会超出一点、被裁掉（比如“毫”顶上的点），所以只能配 D3D11，比软件渲染多占约 50 MB 内存。设置里选“省内存”（software）时自动改用 GDI，文字完整但偏模糊。默认按装机内存定（`Settings::defaultRenderer`）：8 GB 及以上用 D3D11，更小的用“省内存”；旧版留下的“自动”也照这个换算（0.4.0 时门槛是 16 GB，16 GB 的电脑字发虚，issue #1）。
- **界面字体随程序附带**（`fonts\` 下的阿里巴巴普惠体 3.0 常规 / 粗体），缺失时退回系统默认字体（中文系统为微软雅黑），并在 WinShun.log 里记一条警告。程序所在路径不全是 ASCII 时（`D:\软件\WinShun`），字体文件读进内存再装（`addApplicationFontFromData`，约 17 MB）：FreeType 按文件名打开时走 C 运行库，ANSI 代码页放不下的路径打不开，以前这种路径下界面会悄悄变成雅黑（见 pitfalls）。界面里不用 `↵` 这类字体缺字的符号，字体回退一旦触发，内存要多出 30 MB 左右。
- **设置窗口的搜索在侧栏顶部，结果就是原来那些设置行。** 打字时右栏原地筛选：每个 `SettingsSection` 声明自己属于哪一页（`page`）、页里的哪个标签（`tab`），搜索时不分标签，有命中的行才显示，同一页的第一节上方标出页名；行里的开关、按钮照常能用，不用先跳过去。不另写一份“可搜索设置清单”，每个 `SettingRow` 用绑定把自己的标题、说明、控件上的文字（ScopeTabs 的选项、按钮上的字）、补充关键词（`keywords`）、所在页的名字和别名（`pageKeywords`）、节标题、用户填的值（`values`，比如排除的程序）交给 `SettingsSearch.match()`，所以以后加的设置自动能搜到，切换语言也跟着变。行的显示条件写在 `shown` 里而不是 `visible`：`visible` 读出来的是实际可见性，分不清“开关关着”和“这一页没显示”。被开关挡住的行（`unlocks`）命中时，显示那个开关所在的行，注明“打开后可以设置”。↑ ↓ 在结果里移动，Enter 跳到原位（连那一页的标签一起切过去）、滚到那一行、闪一下，有开关就把焦点给开关（不给按钮，免得误按 Enter 清掉东西）。一条都没命中时，用启动器的系统入口检索列出 Windows 自己的设置（`SettingsEditor::findWindowsSettings`）。匹配规则见 `SettingsMatch.h`：标题最重，说明只按字面，分类名和分类关键词三个字母起才按拼音，节的提示语不参与（见 pitfalls.md 的“好几行共用的文字一被命中，整页都出来”）。一屏放不下的页分成几个标签（`SettingsWindow.qml` 的 `pageTabs`，页标题下的 `PageTabs`，Ctrl+Tab 也能切换），平时只显示当前标签的节，每页记住上次停在哪个标签；标签名不进匹配的上下文，否则搜“快捷键”会把整个“快捷键”标签都带出来。

## AI 助手（MCP）

Win顺 是一个 MCP（Model Context Protocol）服务器：Claude Desktop、Claude Code、Cursor、VS Code 等 AI 客户端连上以后，模型可以调用它搜文件名、搜文件内容、列最近改过的文件、看文件夹和文件信息；用户允许时还能打开文件、读剪贴板历史。实现在 `src/mcp/`，按 MCP 2025-11-25 版的规范（也接受客户端报的 2025-06-18、2025-03-26、2024-11-05，原样回给它）。

- **传输：stdio 中继 + 命名管道，不是 HTTP。** AI 客户端一律以普通权限用 stdio 启动 MCP 服务器，而 Win顺 以管理员身份常驻，所以客户端启动的是一个小程序 `WinShunMcp.exe`（Qt Core，无窗口，不提权），它把每行 JSON-RPC 原样转到 Win顺 的命名管道 `\\.\pipe\WinShun.Mcp.<用户 SID>`，Win顺 那边才是真正的 MCP 服务器（`McpServer`，每个连接一个会话，和界面在同一个线程上）。协议只实现一遍，单元测试直接在进程内测；以后的插件系统也可以在这条管道上说同样的 JSON-RPC。没有用 Streamable HTTP：那要在提权进程里开一个本机端口，任何本地程序（包括浏览器沙箱里的网页经 DNS 重绑定）都能摸到，得再做令牌和 Origin 校验；命名管道的 DACL 把访问限在当前用户，标签“中”把低完整性的进程挡在外面，操作系统替我们把关（见 pitfalls 的“管理员进程建的管道”）。管道的客户端一端用重叠 I/O，一个线程读着的时候另一个线程照样能写（pitfalls：“管道一个线程在读”）。
- **中继自己做的事只有三件**：第一次用到时才连管道，断了就在下一个请求时再连（Win顺 可以在客户端之后启动，也可以中途重启，客户端只觉得等了一下）；Win顺 没运行时照样回答 `initialize`（否则客户端会把这个服务器判成坏的）、`tools/list` 回它上次见过的工具（`%LOCALAPPDATA%\WinShun\mcp-tools.json`，Win顺 启动时也写一份）、工具调用回 `isError` 的结果，文字告诉模型请用户启动 Win顺，不用重启客户端；带 `--start-winshun` 参数时，第一次调工具还会试着运行开机自启的计划任务把 Win顺 拉起来（和任务栏按钮一样，不弹 UAC；默认不这样做：Win顺 在运行但没开 AI 连接时，运行那个任务只会让正在运行的那份弹出搜索框，所以先看单实例互斥量，在运行就不碰）。日志写到 stderr，Claude Desktop 把它存成 `mcp-server-winshun.log`。中继重新连上时用客户端的 `initialize` 参数替它再握一次手，会话里的客户端名字不变。
- **工具**（`McpTools.cpp`，描述用英文写给模型看，`initialize` 里的 `instructions` 教它 Win顺 的查询语法）：`search_files`（文件名搜索，走 `SearchEngine` 的“文件”范围，所以拼音、`ext:`、`!`、通配符、路径、最近打开优先这些和搜索框一样；`kind`、`sort`、`limit` 最多 200）、`search_content`（“内容”范围，`timeout_ms` 到了就把已找到的按相关度排好返回，`complete=false`）、`recent_files`（直接并行扫一遍索引按修改时间取最新的，可限定文件夹、扩展名、天数）、`list_folder`（从索引列一个文件夹）、`get_file_info`（从磁盘读大小、时间和属性）、`index_status`，以及开关放行的 `open_item`、`show_in_folder`（`shell::open`，普通权限）、`clipboard_history`、`clipboard_get`。每个工具带 `inputSchema`、`outputSchema` 和注解（只读的 `readOnlyHint`，打开的 `readOnlyHint: false`），结果同时放在 `structuredContent` 和一段同样内容的 JSON 文字里。参数不对、路径不存在这类错误按规范回 `isError: true` 的工具结果（模型能看懂并改参数），不认识的工具才回协议错误。日期一律 ISO 8601 带时区；文件大小从磁盘取，锁外面取。
- **搜索引擎是自己的一个。** `SearchEngine` 只跑最新的一次请求，和启动器共用会把用户正在打的字的搜索取消掉，所以 MCP 有自己的引擎（和对话框旁的搜索框一样）；AI 的搜索也因此一次一个：第二个客户端的请求排队。`notifications/cancelled` 和会话断开都取消在跑的搜索，按规范不再回复。
- **AI 只看得到用户不提权时看得到的东西。** Win顺 是管理员进程，索引里有只有管理员能列出的文件（别的用户的目录、受保护的系统目录），直接按索引回答就等于让普通权限的程序绕过 UAC。所以每个结果都按调用者的令牌做 `AccessCheck`（`Visibility`）：令牌是管道客户端自己的——连接后第一次读到数据时 `ImpersonateNamedPipeClient`，把线程令牌复制成一个模拟令牌交给会话（客户端允许到什么级别就什么级别；中继用 `SECURITY_IMPERSONATION` 连）；没有客户端令牌的会话（进程内测试）用 Win顺 自己的链接令牌（`TokenLinkedToken`：同一个用户去掉管理员组和特权，鉴别级别，`AccessCheck` 够用），没提权时就是进程自己的令牌——从不用 Win顺 的提权令牌。选客户端令牌而不是一律用链接令牌，是因为“不多于调用者自己”更准：提权的终端里跑的客户端本来就看得到一切。检查的粒度：`search_files`、`recent_files`、`list_folder` 看条目所在文件夹的 `FILE_LIST_DIRECTORY`（能列的文件夹里的名字都看得到，和资源管理器一样；列不了的文件夹回“不在索引里”，和不存在的说法相同，不透露它在），按文件夹缓存，每次调用几十到两百次检查；`search_content` 还要文件本身的 `FILE_READ_DATA`（片段是内容）；`get_file_info` 要 `FILE_READ_ATTRIBUTES`，看不到的回 `exists: false`；`open_item` 要能读（文件夹要能列）。被过滤掉的不计数：`search_files` 不再报 `total_matches`，只报 `truncated`。安全描述符用 `GetNamedSecurityInfo` 取（连它都取不到的受保护目录按看不到算），每次检查约 30–60 µs，次数和耗时记在 mcp.log 每一行末尾。
- **安全与隐私**：`[Mcp] Enabled` 默认关，在设置里给某个客户端点“连接”时自动打开；开着时只有只读的工具；打开文件、读剪贴板各有开关，默认关，关着时这两组工具不出现在 `tools/list` 里（开关改了给所有会话发 `notifications/tools/list_changed`），硬调就回 isError 说明在哪打开。“不让 AI 看到的文件夹”（`[Mcp] ExcludedPaths`）在结果里过滤，列目录、看信息、打开也都不行；“不建索引的文件夹”AI 本来就看不到。每次调用记一行到 `%LOCALAPPDATA%\WinShun\mcp.log`（时间、客户端、工具、参数、结果数量、耗时、访问检查次数），剪贴板里的文字不记。管道只有当前用户能连。
- **设置页“AI 助手”**（`AiAccessSection.qml`、`AiClientsSection.qml`）：几个开关、排除的文件夹、打开记录；下面列出装了的客户端，点“连接”把 `WinShunMcp.exe` 写进它的配置（`McpClients.cpp`：Claude Desktop 的 `%APPDATA%\Claude\claude_desktop_config.json`、Cursor 的 `~\.cursor\mcp.json`、VS Code 的 `%APPDATA%\Code\User\mcp.json`，合并进原有的 JSON，先备份成 `.bak`，不是标准 JSON 的（带注释）不动，让用户复制配置自己加；Claude Code 运行它自己的 `claude mcp add --scope user winshun -- <exe>`，找不到 claude 命令就给命令让用户复制）。写进配置的命令带 `--start-winshun`（Win顺 确实没运行时，第一次调工具就把它拉起来）。配置里已经写着这个路径的显示“已连接”；连上的客户端名字（`clientInfo`）和调用次数显示在开关下面。
- **测试**：`tst_mcp` 在临时文件夹上手工填一个索引（`IndexService` 不 `start()`，直接往 `index()` 里加条目），真的 `SearchEngine`、`ToolHost`、`McpServer` 跑在上面：协议、每个工具、取消和排队、真管道、以及用 Win32 管道当 AI 客户端驱动真的 `WinShunMcp.exe`（在线、离线、Win顺 中途退出再回来）。要用真实 AI 客户端试时，`wsbench --mcp-host` 把索引文件复制一份后在 `WinShun.Mcp.<SID>.bench` 管道上提供同样的服务（没有打开和剪贴板），客户端配置里写 `WinShunMcp.exe --pipe <那个名字>`。

## 插件系统

设计方案见“插件系统设计”（2026-10-11 的方案；阶段 0 的实测结论在 pitfalls 的“插件系统（阶段 0：探针）”）。阶段 1 做的是核心库 `src/plugin/`（静态库 `wsplugin`）、runner 程序和单元测试；阶段 2 接进启动器；阶段 3 是设置页；阶段 4 是随包插件、SDK 和模板、给插件作者的文档（`docs/plugins.md`，英文版 `plugins.en.md`：快速开始、manifest 参考、协议、权限表、调试、常见问题）、MCP 桥和安装包（本节末尾几条）。

- **三层插件，一份协议。** 零代码（manifest 的 `run` 是 url / program / folder / search / items，Win顺 进程内直接出结果，复用 `WebShortcut` 的 `%s` 百分号编码）；一次性脚本（`runtime.mode = once`：每次查询起一个进程，查询从 `WS_QUERY`、`WS_TEXT`、`WS_COMMAND`、`WS_TRIGGER`、`WS_KEYWORD`、`WS_MATCH`、`WS_PLUGIN_DIR`、`WS_DATA_DIR`、`WS_SETTINGS`、`WS_LOCALE`、`WS_THEME`、`WS_VERSION` 这些环境变量进，stdout 出一个 JSON 对象、一个数组或纯文本行；动作另带 `WS_ACTION`、`WS_ITEM`）；常驻（`resident`：stdio 上跑 JSON-RPC 2.0 按行：`initialize`、`query`、`query/partial` 通知、`cancel` 通知、`action`、`settingsChanged`、`shutdown`；插件可以发 `winshun/tool`（和 MCP 的工具同名同参数，按 manifest 的权限放行：`winshun:search`、`winshun:open`、`clipboard:read`；`index_status` 总可以）、`winshun/log`、`winshun/notify`、`winshun/progress`）。item 的字段见 `Items.h`。
- **插件进程不由 Win顺 直接起。** Win顺 是管理员进程，阶段 0 实测 `CreateProcessWithTokenW` 不接受句柄列表和缓解策略，所以 Win顺 用资源管理器的令牌（先做硬检查：`TokenIsElevated = 0` 且完整性低于“高”；资源管理器以管理员身份运行或根本没有时，退到自己令牌 `CreateRestrictedToken` 降到中完整性 + `CreateProcessAsUserW`，`Runner::tokenSource()` 记下来，设置页要提示“网络位置可能看不到”；Win顺 自己没提权时就普通 `CreateProcessW`）起**一次** `WinShunPluginHost.exe`，放进只带 `KILL_ON_JOB_CLOSE` 的作业（Win顺 退出或崩溃，runner 和所有插件一起结束）。runner 自己调 `SetProcessMitigationPolicy`（扩展点禁用、镜像加载两项），插件由它用普通 `CreateProcessW` + `STARTUPINFOEX`（只继承三个标准句柄；缓解策略不含 PROHIBIT_DYNAMIC_CODE，解释器要 JIT）+ `CREATE_SUSPENDED` 起，放进带限制的嵌套作业（内存上限、没有 `processes` 权限就 `ActiveProcessLimit = 1`、没有剪贴板权限就 UI 限制里的读/写剪贴板、没有 `ui` 就桌面等限制）再 `ResumeThread`；环境是 `CreateEnvironmentBlock(runner 的令牌)` 加 `WS_*`，提权进程的环境一个都不传。`sandbox: strict` 的插件用 runner 自己令牌降到低完整性起，`<id>.data` 文件夹由 Win顺 打低完整性标签（`S:(ML;OICI;NW;;;LW)`），它写得了那里、写不了用户目录。这些在 `tst_plugin` 里都是读出来验证的（提权跑：完整性 RID、`TokenIsElevated`、Administrators 仅拒绝、登录会话等于资源管理器的、作业限制、缓解位、起子进程报 1816、读剪贴板报 5、低完整性写用户目录报 5）。
- **Win顺 ⇄ runner 的协议**（一根命名管道 `WinShun.Plugin.<SID>.<pid>.<序号>.<随机数>`，Win顺 建、runner 连，安全描述符和 MCP 的管道一样；runner 先说 hello 带上命令行给它的钥匙，Win顺 还核对连上来的进程 pid）：每行 `<实例号> <一行>` 是某个插件的 stdin / stdout 的一行（原样，不再编码；`encoding: oem` 的插件 runner 先把它从 OEM 代码页转成 UTF-8），`_ {JSON}` 是控制消息：Win顺 发 `start`（exe、args、cwd、env、作业限制、strict、encoding、stdin 开不开）、`stop`（结束作业）、`shutdown`；runner 回 `hello`（自己的令牌事实）、`started {id, pid}` / `failed {id, stage, error}`、`stderr {id, text}`、`exited {id, code, stderrTail, overlong}`、`log`。管道断了 runner 结束所有插件自己退出；runner 没了 Win顺 按退避重启它。
- **Host 的行为。** 每次按键 `Host::query(text, scope, queryId)`：只有“全部”触发；先取消所有在途查询（常驻的发 `cancel` 通知、once 的结束进程），再按 Catalog 的匹配分发（至多一个关键字匹配，然后正则和推送触发器）。常驻插件没起就起（起的期间最新的一次查询等着，中间的丢）；once 插件按 `debounceMs` 防抖（默认 120）。每次查询一个超时（resident 默认 1500 ms，once 3000），到点就 `queryFailed`，晚到的响应按 queryId 丢；常驻连续 3 次超时当挂死，结束后退避重启。退出码非 0 或没叫它退就退了算崩溃：退避 1 → 5 → 30 秒，5 分钟内 3 次就停用（`disabledAfterCrashes`）；`idleExitSec`（默认 600）没用到就发 `shutdown` 让它退出；常驻数超过 `maxResident`（8）时最久没用的先退（eager 的不算）。所有等待都在 runner 的管道线程和 QTimer 上，GUI 线程只收 queued 调用。

- **随包插件、SDK 和模板（阶段 4）。** 仓库 `plugins/` 下六个插件（`docs/plugins.md` 的“随 Win顺 装好的插件”），构建时 `bundled_plugins` 目标把它们连同各自用的 SDK 文件和 `WinShunTools.exe` 整理到 `build\<preset>\plugins`（App 把 `<exe 目录>\plugins` 当随包目录，所以开发构建和安装后一样），`build.ps1 -Deploy` 原样放进 `dist\WinShun\plugins`，Inno Setup 的 `recursesubdirs` 跟着打包；全部默认停用。SDK 在 `src/plugins-sdk/`（只此一份：编成资源 `:/sdk/` 给“新建插件…”复制，随包插件由构建复制）；模板五种（PowerShell 常驻、Python 一次性、Python 常驻、C++ 常驻、零代码），都写在 SDK 上。`winshun.tools` 跑在 strict 沙箱里（`wsbench --plugin` 现在把插件进程的完整性、是否提权、是否在作业里读出来打印：LOW (4096) / no / yes）。零代码 `items` 的 `open.path`、`subtitle` 里的 `%VAR%` 会展开（随包的 `winshun.go` 要写一次到处用）。
- **MCP 桥（阶段 4，方案 §6.2）。** `plugin::AiBridge`（`src/plugin/AiBridge.{h,cpp}`，App 在 `applyMcp` 建、`applyAiBridge` 从 `applyMcp` 和 `applyPlugins` 两边同步）：`[Mcp] Plugins` 开着时，manifest 写了 `ai.expose` 且卡片上“给 AI 用”（`[Plugin.<id>] Ai=`）没关的插件，每个命令一个 `mcp::ExternalTool`（`plugin_<id>_<command>`，id 里的点换下划线；`readOnlyHint`；`openWorldHint` = 声明了 `network`；输入 `{query, limit}` 或命令的 `ai.parameters`；输出 `{items: [{id, title, subtitle, url?, path?, copy?, informational?}], returned}`，不含 `data`），`[Mcp] PluginActions` 开着再加 `_run`（`destructiveHint`；参数 `{query, item_id, action?}`：重新查一次、按 id 找到行、`Host::action`，回 `{done, message, effects}`；行的默认动作是 `open` / `setQuery` / `search` 的告诉模型让用户自己开）。`ToolHost::setExternalTools` 整表替换（在途的调用攥着自己那个 `shared_ptr<Tool>`），`toolsChanged` 只在可见的名单变了时发（McpServer 据此发 `list_changed`，App 重写 `mcp-tools.json`）；停用的插件工具保留但 `offered = false`，`ToolHost::offReason` 让 McpServer 回“The plugin 'X' is turned off…”。调用走 `Host::callCommand`：不经过 `Host::query` 的 `cancelAll`（用户打字不会取消 AI 的调用，AI 的调用也不取消用户的），自己一个计时器（`timeoutMs × 3`，AI 不是在打字），常驻插件没起就起、`initialize` 回了再发（`flushCommandCalls`），一次性插件走 `launchOnce` 带 `commandCall` 标记，结果不走信号直接回调。`tst_mcp::pluginTools` 用零代码插件和 `plugin_fake --serve` 经 runner 跑完这一套（总开关关着没有工具、开了有、调用返回、动作默认没有、停用的提示文字、卡片开关）；`wsbench --mcp-host --plugins DIR` 把一个文件夹的插件当工具提供在测试管道上。
- **实测（阶段 4，`wsbench --plugin`，未提权，2026-10-11；冷启动含 runner）：** winshun.tools（C++，strict）冷启动 22–98 ms，稳态 0.07–0.15 ms；winshun.kill（PowerShell 5.1 常驻）冷启动 290–320 ms，稳态 14–20 ms（`Get-Process` 一遍；窗口标题和路径只对列出的行读，之前对每个进程读 `MainWindowTitle` 要 2.5 秒）；winshun.translate（Python 常驻，未配置）冷启动 128 ms，稳态 0.09 ms；winshun.bookmarks（Python 一次性，读 Chrome / Edge 的书签文件）每次 155–190 ms；零代码 0.0 ms。`wsbench --launcher-sim --plugins build\release\plugins`：`= 1+2*3` 关键字模式 0.7 ms 出 4 行；`#ff8800`、`12 inch to cm` 推送行与名字结果一起显示（插件 0.5–0.9 ms）；`report` 与没有插件时 100 行逐行相同。MCP：经 `WinShunMcp.exe` 调 `plugin_winshun_tools_calc` 首次 30 ms（含起进程），之后 0.4–0.5 ms；`plugin_winshun_kill_kill` 277 ms（含起 PowerShell）。
- **`.wsplugin` 文件关联：这次不做。** WinShun.exe 的清单是 requireAdministrator，双击 `.wsplugin` 起的第二个实例要先过 UAC 才能把路径转给运行中的那份（`WM_COPYDATA` 对不提权的发送者关着，所以也不能让不提权的 `WinShunSearch.exe` 代转）——每装一个插件弹一次 UAC 不值。拖到设置页、“添加插件…”都已经认 `.wsplugin`。

## 已知限制和后续可做的

- 拼音只认读音的开头，不做模糊纠错；排除词（`!xx`）只按字面匹配，不按拼音。
- 内容索引不记带重音的字母、西里尔字母等，也不记一两个字母长的英文：搜这些时仍要逐个读文件（结果边找边出）。U 盘等非 NTFS 磁盘上的文件不建内容索引，也是逐个读。
- 内容索引第一次建立时，时间几乎都花在 Windows Defender 扫描每个打开的文件上（每个约 7 ms CPU，在 Defender 自己的进程里）。同时读几个文件，它就大约占几个核：有人用电脑时读 CPU 核数的 1/4 个（作者电脑 32 线程：8 个，每秒约 1200 个文件），两分钟没碰键盘鼠标、接着电源、没有全屏程序（电影、游戏、幻灯片）时读一半（16 个，每秒 2000–4000 个），用户一回来 2 秒内降回去。读线程不用后台模式：那样磁盘请求降成“极低”，Defender 的扫描跟着变慢，开多少线程都只有每秒一两百个（旧版 33 万个文件要 25 分钟，见 pitfalls）。用户文件夹里的文件先读；机械硬盘上的同时最多读 2 个。建好之前内容搜索仍会逐个读还没收录的文件，读过的顺带记进索引。
- 文档：扫描版 PDF 和图片里的文字读不到（没有文字识别）；加了密码的读不到；xlsb、OpenDocument（odt / ods / odp）、RTF、EPUB、OFD 还不支持。Word 文件只有被 Word 排过版（存着分页位置）才显示页码。
- 名字里的非英文字母（如 `Ä`/`ä`）不区分大小写的匹配只对英文字母生效。
- 没有 Listary 那种嵌进资源管理器窗口里的搜索；“打开 / 保存”对话框认资源管理器、Total Commander 和 Directory Opus，XYplorer、OneCommander、Files 等别的文件管理器还不认（XYplorer 和 OneCommander 有对外接口，Files 没找到）。在文件管理器前面搜到文件夹时，也不会让那个窗口直接跳过去，而是另开。程序自己画的对话框（Qt、Java、GTK 等的非系统对话框）和老式的“浏览文件夹”树形对话框不支持。
- 非 NTFS 磁盘（U 盘、exFAT/FAT）在程序没运行期间的改动，要靠启动后的后台同步补上（约十几秒内完成）；弹出后又取消的非 NTFS 磁盘会重新遍历一次。
- 代替任务栏搜索：Windows 自带的搜索按钮要用户自己在任务栏设置里隐藏；搜索框只放在主任务栏上，资源管理器重启后重新挂上、浅色任务栏、自动隐藏还没实测，启动器被拖离框以后打的字仍显示在框里；首页只有常用应用和最近打开的，还没有常用设置；在开始菜单里打字时，按住 AltGr 打出的字符（欧洲键盘）不截，仍进 Windows 搜索。多显示器、任务栏自动隐藏、竖任务栏、100%/125% 缩放和 Windows 10 还没实测。
- 剪贴板历史：多选时不能把图片和别的内容合在一起粘贴，图片要一张一张地粘贴；还没有“依次粘贴”（每按一次 Ctrl+V 贴出下一条）。自己画光标又不告诉系统的程序（一些游戏、少数自绘的编辑器）里，剪贴板开在鼠标指针处；新版记事本和 Office 还没实测过找光标。终端里只有 mintty 和 PuTTY 用 `Shift+Insert`，其他不接受 `Ctrl+V` 的程序要自己按它们的粘贴键。
- 文件夹被隐藏或取消隐藏时，里面已有文件继承来的“隐藏”标记不会马上跟着变，要到下次重新读取该盘时才更新。
